# ADR 0020: 항만 관제 패턴은 운영 현황의 계획 기준 표시로만 가져온다

날짜: 2026-11-04

상태: 수락(2026-11-04, 사용자 결정 "서로 토론해서 ADR로 결정해서 처리"). 1단계를 구현했다.
- 구현됨: 운영 현황의 「확인이 필요한 것」 띠, 반출 1건당 계획상 재취급 이동, 관측 점유율, 현재 검토 목록 표(계획한 팔·계획 생성), 실제 완료량과 실행된 재취급 이동(결정 6, 2026-11-04 추가).
- 2단계(2026-11-04, 사용자 결정 "남은 일 처리"): 실제 완료량(결정 6), 업무 타임라인(결정 7), 반출 작업 공간의 칸별 점유 높이·재취급 예정 칸(결정 8).
- 3단계(2026-11-04, 사용자 결정 "그것까지 바로 처리"): 감사 기록 기반 상태 전이(결정 9), 시간당 물동량(결정 10), 연결 평면의 점유 표시와 3D 화물 라벨(결정 8 확장).
- 거부: 장비 상태판(재논의 조건은 아래). 교대·일 단위 처리율과 TEU·ton 환산은 미집계.
- 잇는 결정: ADR0005(팔 구분·S 외부 단계)·ADR0011(계획과 실적 분리)·ADR0013(완료는 업무 장부)·ADR0018(장치 상태는 R)·ADR0019(실적 미집계 유지).

## 배경

[항만 관제 조사](../research/2026-11-04-port-control-benchmark.md)에서 부산항 Port-i, 로테르담 PortXchange, HHLA, Navis N4의 관제 화면을 살폈다. 반복되는 요소는 예외·알림, KPI, 작업 목록, 시간축, 장비 상태판이다. Harbor는 그중 TOS 야드 계획과 ECS 작업 지시·예외에 해당한다. 재취급 최소화는 실제 터미널의 야드 효율 지표이기도 하다.

세 관점(관제 UX·구조와 진실성·최소 범위)으로 두 차례 토론했다. 모두 동의한 원칙은 "실제 항만 수치·화면을 흉내 내지 않고 구조만 가져오며, Harbor가 가진 근거만 보인다"이다.

## 결정

1. **관제 패턴은 「계획 기준 표시」로만 가져온다.** 새 값은 `harbor_web/operations.py`의 읽기 모델에서 이미 저장된 관측·계획·인계로 계산한다. 새 표, Fleet 호출, Fleet 상태 해석, GET에서의 쓰기는 없다(ADR0013 결정 8). 계획 값(`workload`)과 실적 값(`actual`)은 다른 키로 두고, 실적은 결정 6의 완료 근거로만 세고, 근거가 없는 처리율은 `None`이며 「미집계」로 보인다(ADR0019).
2. **「확인이 필요한 것」 띠를 운영 현황 맨 위에 둔다.** 기존 값만 모은다. 관측 없음, 관측 유효 시간 밖·같은 출처의 새 관측(`freshness`), HOLD 계획, 재검토로 이동 집계에서 빠진 계획(관측 자체가 무효이면 그 한 줄로 대신한다), 대조가 필요한 인계(`UNKNOWN`·`DISPATCHING`·`CANCEL_PENDING`·`BLOCKED`)다. 인계는 관측에 묶이지 않으므로 「전체 인계」로 범위를 밝힌다. 인계 이름은 `COMMAND_LABELS` 그대로, 조치는 원래 작업 화면으로 가는 「원래 작업 대조」 하나다. 제목의 건수는 항목 건수의 합이다. 재전송을 암시하는 버튼·문구는 두지 않는다(ADR0013 결정 5). 0건이어도 「0건 · 관측 #N 기준」으로 보여, 정상과 표시 실패를 구분한다.
3. **반출 1건당 계획상 재취급 이동(예상).** 선택 관측에 고정되고 인계 전인 유효 READY 반출 계획만 센다. 분자는 그 계획들의 재취급 단계 이동 수, 분모는 그 계획 수다. 입고·재배치 계획은 분자와 분모 모두에서 뺀다. 분모를 함께 보이고(「재취급 N회 ÷ 반출 계획 M건」), 분모가 0이면 「대상 반출 계획 없음」으로 쓴다. 「지시 전 계획 · 실적 아님」을 숫자 바로 아래에 둔다.
4. **관측 점유율.** 관측 한 장의 점유 칸 ÷ 전체 칸이다. 관측 번호와 단위(격자 칸·적재 자리)를 함께 보이고, 유효 시간 밖이면 경고한다. 보관·임시 장치·반출대별 점유는 기존 영역 목록에 따로 남긴다.
5. **현재 검토 목록을 작업 목록 표로 바꾼다(N4 Job list 모양).** 열은 화물·요청, 상태, 계획한 팔(주·대안), 계획 생성이다. 팔 값은 저장된 계획의 `moves[].primary_arm`·`alternate_arms`만 읽는다. 다시 계산하지 않는다(ADR0005 결정 4). 공급암 S는 계획 이동 밖의 외부 단계(ADR0005 결정 5, `harbor/site.py`)라 이 열에 나오지 않음을 표 설명에 적는다. 「담당 장비」·「실행 시각」이라 부르지 않는다. 실제 배정과 실행은 Fleet 소유다.
6. **실제 완료량과 실행된 재취급 이동은 `COMPLETED` 인계만 센다.** Command가 `COMPLETED`가 되는 곳은 `commands.advance_command` 두 곳뿐이다. 둘 다 장부 행이 `execution_kind=ARM_TRANSFER`이고 저장된 binding과 digest가 같음(`_check_ledger_binding`)을 확인한 뒤, 업무 장부 `finish()`가 쓴 `COMPLETED`를 옮긴다. 셀 단계 레거시 경로(`ProcessBinding`)는 Command를 만들지 않으므로 이 수에 들어올 길이 없다. 완료량은 요청 단위로 한 번만(같은 요청의 새 완료는 대체한다) 요청 종류(반출·입고·재배치)별 건수로, 실행된 재취급 이동은 완료된 반출 인계의 binding에서 반출 이동 앞의 이동 수로 센다. binding은 장부와 대조된 불변 값이라 다시 계산하지 않는다. binding에서 반출 이동을 찾지 못한 완료 반출 인계가 하나라도 있으면 재취급 이동 합계를 0이 아닌 「미집계」로 두고, 그 인계를 「확인이 필요한 것」 띠에 「원래 작업 대조」로 올린다. 실제 Command는 장부 준비 단계에서 같은 binding을 검사하므로 이 경우는 생기지 않아야 하며, 생기면 덜 센 숫자 대신 결손으로 보인다. 범위는 관측에 묶이지 않는 「전체 출처」다. 처리율·시간당 물동량은 집계 시간 기준이 정해지지 않아 「미집계」로 남긴다. 같은 기준으로, 장부가 완료한 반출 요청은 뒤 순위 반출을 더 막지 않는다(`plan_service._open_outbound_ahead`, 재배치의 `outbound_pending`과 같다). 요청에는 닫힘 상태가 없어, 화면 확인 전에는 반출 하나를 끝내도 다음 순위가 계속 `PRIORITY_ORDER_BLOCKED`였다. 완료는 대기열에서 빠지는 일이므로 대기열 지문(`queue_digest`)에도 넣어, 그 전에 세운 계획은 재검토로 표시된다(완료가 하나도 없으면 지문은 이전과 같다). 열린 반출 판단은 `order_queue.open_outbound_orders` 하나로 모았다. 재배치가 쓰는 반출 일정 순위에는 완료된 요청도 남긴다(설계 32). 운영 현황의 「지금 필요한 조치」도 완료 업무를 「업무 완료」로 맨 아래에 두고 타임라인으로 잇는다.
7. **업무 타임라인은 요청 하나를 두 줄로 보인다**(`/requests/<id>/timeline/`, `harbor_web/order_timeline.py`). 계획 줄은 Plan과 그 예상 단계다. 단계는 시각이 없는 `Plan.result['moves']`의 순서라 「예상」으로만 보인다. 실제 줄은 시각이 있는 기록만 담는다: Command 생성, 상태 전이(결정 9), `CommandFact`, `EvidenceSubmission`(대조 전 표시), `FieldConfirmation`, `DepartureIntent`. 모든 사건에 출처 종류·id를 붙인다. 업무 완료는 Command `COMPLETED`뿐이다. 단계 판정은 운영 현황과 같은 `move_phases`를 쓴다.
8. **반출 작업 공간에 칸별 점유 높이와 재취급 예정 칸을 서버 렌더 평면표로 둔다**(`harbor_web/yard_occupancy.py`). 점유 높이는 관측 단계의 층 수(0·1·2·3층 이상)다. 다칸 화물은 한 개체로 세고 걸친 모든 칸에 표시한다(ADR0008). 재취급 예정 칸은 저장된 계획 이동의 재취급 단계 화물이다(저장된 `phase_label` 우선). 색만 쓰지 않고 글자·점선·화면 낭독용 라벨을 함께 두며, 범례에 「계획 기준 · 실적 아님」을 밝힌다. 기존 층별 평면과 3D 보기, 연결 선택은 바꾸지 않는다. 연결 평면(`yard-selection.mjs`)도 현재 보는 단계의 배치에서 같은 규칙으로 칸별 점유 높이를 계산해 「점유 N층」 칩으로 보이고, 단계를 바꾸면 갱신한다. 재취급 예정 화물은 서버가 저장된 계획 이동에서 뽑은 `scene.rehandle`로 받는다(가상 배치 편집 중에는 끈다). 3D에는 새 색 단계를 두지 않는다. 3D에서 점유 높이는 상자 높이 자체이고, 재취급 대상은 이미 범례가 있는 `blocker` 색으로 구분된다. 공간 계획에서는 재취급 단계 화물, 기존 셀 관측에서는 반출 대상 위 화물이다. 화물 정보 줄에만 「재취급 예정 · 계획 기준」을 덧붙인다.
9. **Command 상태 전이는 기존 감사 기록에서 읽는다. 새 표를 만들지 않는다.** Command 상태를 바꾸는 곳은 `commands._save` 하나뿐이고, 같은 트랜잭션에서 수정·삭제할 수 없는 `Audit`(`action=command.<상태>`, `created_at`)를 쓴다. 타임라인의 실제 줄은 이 행마다 「지시 → 상태」를 「Harbor 저장 시각 · 감사 기록 번호」와 함께 보인다. ROSY 조회 시각과 같은 줄에 정렬되지만 로봇 동작 시각이 아니다. 업무 완료도 `command.completed` 감사 행이 있어야 보인다. 감사 행 없이 상태만 바뀐 Command는 전이로 보이지 않는다.
10. **시간당 물동량은 첫 완료와 마지막 완료 사이의 간격 속도로 센다.** 크레인 생산성처럼 첫~마지막 작업 구간을 쓰되, 그 구간 안의 간격은 「건수 − 1」개이므로 「(건수 − 1) ÷ (마지막 완료 − 첫 완료)」로 계산한다. 대상은 최근 24시간 안에 `command.completed` 감사 행이 있는 완료 인계다(요청당 하나, 그 Command가 처음 완료로 기록된 시각, 조회도 24시간 안으로 한정). 시각은 Harbor가 완료를 저장한 시각이며 로봇이 끝낸 시각이 아니다. 장부가 이미 끝난 것을 나중에 읽은 경우에는 더 늦다. 첫~마지막 간격이 10분 미만이면 시간당 값으로 바꾸지 않고 건수만 보인다. 교대·일 단위 처리율과 TEU·ton 환산은 미집계다.

## 대안

| 대안 | 판단 |
|---|---|
| 실제 항만처럼 선석 간트·선박 일정·장비 상태판까지 갖춘다 | 데모 효과는 크지만 근거 없는 선박·장비 값을 합성하게 된다. 채택하지 않는다 |
| ADR 없이 ADR0019 「다음 단계」에 한 줄만 더한다 | 표시 변경만이면 충분하다는 의견이 있었다. 장비 상태판 거부와 재논의 조건, 계획/실적 라벨 규칙을 번복하지 않도록 따로 남긴다 |
| **기존 계산을 관제 형식으로 다시 배치하고 계획 기준임을 밝힌다** | 쓰기 경로와 경계를 바꾸지 않고 관제 화면의 구조를 보인다. **채택** |
