# ADR 0024: 반출 우선순위를 3단계로 묶고, 단계 안 순서는 시뮬레이션 추천을 사용자가 확정한다

날짜: 2026-11-07

상태: 제안(2026-11-07). 3단계는 11/05 데일리 회의 결정이고, 단계 이름(긴급 / 우선 / 일반)과 단계 안 추천 방식은 서정민 님 제안이다. 팀 확정 전이다(KAN-116).

- 번호: 병합 시점 `main`의 ADR 번호를 다시 확인한다.
- 잇는 결정: ADR 0010(입고 우선순위를 반출 순서로 쓰지 않는다), ADR 0012(실행은 사용자가 확정한다), ADR 0014(완전한 계획끼리 비교, 한도 안 최선 표시), ADR 0020(GET에서 쓰지 않는다).

## 배경

반출 순서는 `Order(priority_group, sequence, tie_policy)`다. 그룹 수에 상한이 없어 사용자가 1 · 2 · 3 · 4… 숫자를 기억하고 맞춰야 했다(KAN-115 2-1). 11/05 회의는 반출 · 입고 우선순위를 3단계로 나누기로 했다. 같은 단계에 요청이 여럿이면 어떤 순서로 꺼내야 재취급이 적은지 사용자가 알기 어렵다.

## 결정

1. **3단계는 기존 필드에 대응한다.** `priority_group` 1 · 2 · 3 = 긴급 · 우선 · 일반. 저장 형식은 바꾸지 않는다. 화면과 입력만 3단계다. 3보다 큰 기존 그룹은 일반으로 읽고, 반출 순서를 저장하면 일반 단계로 다시 번호가 매겨진다.
2. **반출 순서 편집기는 항상 세 칸이다.** 빈 단계도 남아 끌어 놓을 자리가 된다. 단계 i의 j번째 = `(i, j)`이다. 끝난 반출의 `(group, sequence)` 자리는 다시 쓰지 않도록 번호는 그 위에서 시작한다. 단계 안 순서 정책(`tie_policy`)이 같아야 하는 범위는 열린 반출만이다.
3. **단계 안 순서는 시뮬레이션으로 추천한다.** 단계에 요청이 두 건 이상이면 선택 관측 위에서 꺼내는 순서 후보마다 기존 단건 계획기(`plan_spatial`)를 차례로 돌린다. 계획 이동을 적용하고 꺼낸 화물은 야드에서 빼며 다음 화물을 계산한다. 비교는 끝까지 계산됨 → 총 이동 → 재취급 → 원래 순서 순이다. 4건 이하는 모든 순서를, 그보다 많으면 매 단계 가장 싼 다음 반출을 고른다(한도 안 추천으로 표시). 단계는 앞 단계의 추천 순서가 남긴 야드에서 이어서 계산한다.
4. **추천은 보여 주고, 확정은 사용자가 한다.** 가장 좋은 시나리오를 먼저 보이고, 다른 시나리오 하나를 접어 둔다(추천 개수 2, 11/07 사용자 결정). ‘추천 순서로 시행’ · ‘이 시나리오로 교체’를 누르면 그 단계만 그 순서(순서 고정)로 저장된다. 순서가 바뀐 요청은 새 revision이 되어 계획을 다시 검토한다. 계산은 조회 때 하고 저장하지 않는다(ADR 0020).
5. **입고 단계는 처리 순서로만 쓴다.** 입고 요청도 1 · 2 · 3 단계를 받지만, 입고 위치를 정하는 반출 순서로 쓰지 않는다(ADR 0010). 입고 자리 예약 순서에 단계를 반영하는 일은 이 결정에 들지 않는다.

## 결과

- 사용자는 숫자 대신 단계를 고르고, 단계 안 순서는 추천을 보고 정한다.
- 시뮬레이션은 계획 결과를 바꾸지 않는다. 실제 계획은 지금처럼 요청마다 만들고, 실행은 ROSY가 승인한다.
- 조회할 때마다 계산한다. 1×3 컨테이너 3×3×3 야드에서 단계당 4건이면 24개 순서를 끝까지 계산한다.

## 남은 결정

- 단계 이름 팀 확정(KAN-116).
- 버튼 없이 추천 순서를 자동으로 적용할지(지금은 사용자가 한 번 확정).
- 입고 단계를 자리 예약 순서에 넣을지(ADR 0010 변경 여부).
