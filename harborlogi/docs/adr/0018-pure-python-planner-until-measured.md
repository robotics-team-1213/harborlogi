# ADR 0018: 계획기는 측정으로 필요가 확인될 때까지 순수 파이썬으로 둔다

날짜: 2026-11-01

상태: 수락. Rust·C 확장과 JIT는 도입하지 않는다. 아래 재검토 조건이 운영 기록으로 확인되면 다시 결정한다.

## 문제

rustbpe처럼 무거운 루프를 Rust 확장(PyO3·maturin)으로 옮기면 파이썬에서는 import만 바꿔 빨라질 수 있다. Harbor에도 그런 병목이 있는지, 있다면 네이티브 확장으로 풀지를 정해야 한다. 확장을 넣으면 팀원 모두가 Rust 도구 사슬과 플랫폼별 wheel 빌드를 갖춰야 하고, 지금은 CI(Python 3.10·3.12 unittest)가 순수 파이썬만 전제한다.

## 측정 (2026-11-01, `origin/main` 7986d83, 노트북)

- 전체 시험 191개를 cProfile로 돌렸다. 자기 시간 11.7s 가운데 대부분은 SQLite(`__exit__`·`executescript`·`execute` 3.4s)와 소켓 대기(`select` 2.5s)였다. CPU를 쓰는 Harbor 계산은 `harbor/spatial.py`의 `plan_spatial` 탐색 하나였다(누적 2.84s, 45회).
- 프로파일러 없이 호출마다 시간을 재면 `plan_spatial`은 중앙값 0.5ms, 최대 533ms였다. 최대값은 탐색 한도 `SPATIAL_SEARCH_LIMIT`(상태 20,000개)에 닿는 시험 경우다. `plan_rearrangement`는 중앙값 3.0ms, 최대 68.7ms였다.
- 탐색 시간의 대부분은 상태 객체를 만들고 검증하는 데 쓰였다. `with_placements` 1.84s 가운데 `__post_init__` 검증이 1.62s(36,434회)였고, `cells`·`shape`·`identifier`가 수십만 번 불렸다. 탐색 알고리즘 자체의 연산보다 파이썬 객체 생성 비용이 크다.

## Rust로 옮겼을 때 얻는 것 (상한)

- 탐색을 Rust로 옮겨서 파이썬 시간이 0이 된다고 가정한다. 이것이 이득의 상한이다.
  - 보통의 계획은 호출당 0.5ms 이하만 줄어든다. 사용자는 이 차이를 느낄 수 없다.
  - 최악의 경우는 한도에 닿는 호출이다. 여기서 줄어드는 시간은 최대 약 0.5s다.
- 탐색 크기는 이미 정해져 있다. 야드 치수 검증이 행·열 12, 층 6까지이고, 상태 수 한도는 20,000이다. 그래서 실제 야드가 커진다고 시간이 끝없이 늘지 않는다.
- 따라서 Rust의 실익은 응답 속도가 아니다. 같은 시간 안에 더 많은 상태를 탐색해서 계획 품질을 높이는 데 있다. 이 실익은 한도에 닿는 일이 운영에서 실제로 반복될 때만 생긴다. 지금은 그런 기록이 없다.
- 측정의 한계:
  - 노트북 한 대에서 한 번 쟀다.
  - 대상은 시험 고정 사례다. 운영 야드의 화물 분포에서 탐색 시간과 한도 도달 빈도는 아직 재지 않았다.

## 결정

1. **지금은 네이티브 확장·JIT를 넣지 않는다.** 보통의 계획은 1ms 미만이다. 최악의 경우도 ADR0014의 탐색 한도가 시간을 묶는다. 한도에 닿으면 HOLD나 `search_complete=false`로 드러난다.
2. **재검토 조건.** 다음 중 하나가 운영 Plan 기록으로 확인되면 다시 결정한다.
   - 실제 야드에서 `SPATIAL_SEARCH_LIMIT_REACHED`나 `search_complete=false`가 반복되어 계획 품질이 떨어진다.
   - 계획 요청이 화면에서 기다릴 만큼(1s 이상) 오래 걸린다.
   - Harbor를 Raspberry Pi급 장비에 배포한다.
     - Pi 5는 시험 PC보다 단일 코어가 약 3~4배, Pi 4는 약 9~12배 느리다(Geekbench 6 단일 코어 기준, ROSY D-953).
     - 따라서 한도 도달 0.53s는 Pi 4에서 약 5~6s가 될 수 있다.
     - 배포 전에 그 장비에서 계획 시간을 잰다.
   시험 고정 사례의 wall-clock만으로는 결정하지 않는다(ADR0014 3).
3. **재검토할 때의 순서.**
   1. 먼저 파이썬 안에서 줄인다. 탐색 중 상태 복제·검증을 줄이는 자료 구조가 첫 후보다. 검증은 신뢰 경계(입력 스냅샷)에 그대로 남긴다.
   2. 그래도 부족하면 탐색 함수 하나만 PyO3 확장으로 옮긴다. 이때 순수 파이썬 구현을 대조 기준으로 남긴다. 같은 입력에 같은 계획·점수·종료 이유가 나오는지 시험으로 확인한다. ADR0014가 요구하는 작은 전수 탐색 검증도 그대로 둔다.
   3. 시간이 남는다는 이유로 탐색 한도를 바로 올리지 않는다. 한도를 바꾸려면 ADR0014의 기록 항목과 함께 따로 결정한다.

## 결과

- 팀원은 지금처럼 파이썬만으로 개발·시험한다. CI와 설치 절차도 그대로다.
- 대형 야드에서 계획 품질이 탐색 한도에 묶이는 일은 생길 수 있다. 그 신호는 Plan 결과에 남는 종료 이유로 확인한다.

## 대안

- **`plan_spatial` 탐색을 지금 Rust로 옮기기:** 지금 측정으로는 사용자가 체감할 이득이 없다. 대신 도구 사슬·빌드·리뷰 비용이 팀 전체에 생긴다. 기각.
- **numba로 탐색 가속:** 탐색 상태가 dataclass·dict 중심이라 numba가 다룰 수 있는 숫자 배열 형태가 아니다. 쓰려면 사실상 다시 짜야 한다. 기각.
