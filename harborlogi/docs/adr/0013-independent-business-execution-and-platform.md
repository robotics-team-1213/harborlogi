# ADR 0013: Harbor 업무 실행과 ROSY 플랫폼의 독립 경계

날짜: 2026-10-26

상태: 책임 분리 결정 수락. 현재 구현·검증 범위와 남은 운영 수용 조건은
[상세설계24](../design/24-business-execution-boundary.md)의 「지속 실행과 복구」와
「검증과 현재 결손」을 따른다. 설계 결정 수락을 실물·운영 수용으로 계산하지 않는다.

## 배경

사용자는 Harbor에서 재배치를 확정하면 그 목표까지 업무가 진행되기를 요구했다. 첫 실행 요청만 전송하는 ADR0012의 변경으로는 여러 단계의 결과 확인·후속 작업·변경 대응을 충족하지 못한다. 동시에 Harbor와 ROSY는 독립 제품이어야 하며 내부 구현이나 항만 의미를 공유해서 결합하지 않는다.

2026-10-26 결정 당시 `harbor/workflow.py`에는 단계별 업무 장부와 근거 대조가 있었고
`harbor_web/commands.py`가 ROSY 요청·조회와 장부를 조립했다. 당시에는 웹 사용자의
제출·대조 호출만 있었고 상시 업무 실행기는 연결되지 않았다. 기존 장부·어댑터를
활용하되 그때의 결합을 정식 인터페이스로 고정하지 않는 것이 이 결정의 배경이다.

## 결정

| 소유자 | 판단하고 저장하는 것 |
|---|---|
| Harbor | 목표 배치, 화물 점유 크기·업무 우선순위, 재취급·반출·재적재 의존 관계, 사용자 확정, 업무 실행 상태, 재계획, 업무 완료 |
| ROSY Fleet | 인증된 요청의 접수·승인, 실제 자원 배정·claim, 설치 정책·안전 검사, 실행 수명주기·취소와 상태 조회 |
| ROSY World·장치 owner·인증된 producer | 물리 관측과 장치 제어·정지, 소유 계약에 따른 실행·위치·퇴피 근거 |

Harbor의 **업무 실행기**는 확정 목표의 남은 작업을 지속적으로 진행한다. 업무 규칙으로 다음 단계를 선택하고, ROSY 연동 어댑터를 통해 요청하며, 실행 결과와 필요한 업무 근거를 확인한 뒤 후속 단계로 간다. UI·자연어 입력은 같은 application service에 사용자 결정을 전달한다. 브라우저를 닫아도 접수된 업무가 소실되거나 다음 단계를 기다리지 않아야 한다.

ROSY는 ‘C2가 C1의 반출을 방해한다’는 항만 규칙을 몰라도 된다. Harbor의 업무 계획 전체나 재취급 상태 머신을 실행하지 않는다. 공개 계약으로 지원하는 도메인 중립 작업과 설치된 object/source/target 참조를 받아 실행한다. ROSY의 기하·충돌·로봇 경로·device 재시도·정지 판단을 Harbor에 복제하지 않는다.

## 결합을 제한하는 규칙

1. 서로의 Python 모듈·DB·ORM·내부 이벤트 버스를 공유하지 않는다. 외부 경계는 버전이 명시된 공개 API와 인증된 관측 계약이다. 공유 코드가 필요하면 별도 계약 산출물로 검토하며 플랫폼 내부 라이브러리를 앱에 끌어오지 않는다.
2. Harbor 실행기는 앱 소유의 단계 식별자·정규화 결과를 사용한다. wire 경로·응답 스키마·ROSY 상태 코드는 어댑터에서 검증·변환한다. 원본 key·mission·attempt·digest·principal·관측 시각은 근거로 보존하고, 정규화하면서 버리거나 새 값으로 대체하지 않는다.
3. Harbor의 목표/계획 revision과 ROSY의 generation·authority epoch·관측 revision을 같다고 가정하지 않는다. 각 값은 소유자가 검증한다. 검토된 설치 대응은 버전과 digest를 보존하고 변경되면 새 요청 전 재검증한다.
4. 앱의 계획상 예약은 ROSY 자원 claim이 아니다. Harbor는 작업 후보·필요 조건을 표현할 수 있지만 실제 배정·점유·안전 판정은 ROSY가 수행한다. 설치된 capability/관측 계약으로 확인할 수 없는 지원을 추측하지 않는다.
5. 실행 불명은 독립 상태다. 원래 요청 key로 대조하고, timeout이나 통신 단절만으로 완료·실패·정지·점유 해제를 확정하지 않는다. 결과 불명 작업에 새 key를 만들어 재전송하지 않는다.
6. 정상 업무의 단계 진행은 Harbor가 담당한다. ROSY는 로봇 동작 내부의 진행·복구를 담당한다. Harbor는 장치 저수준 단계를 반복 실행하거나 자동 재무장하지 않는다. 취소 접수와 실제 정지·자원 해제를 구분한다.
7. 재계획은 아직 제출하지 않은 후속 작업을 대상으로 한다. 이미 제출한 작업은 원래 계획과 식별자에 고정한다. 진행 중 상태가 안정적으로 대조된 뒤 새 계획으로 연결하며, 사용자 확정 범위를 벗어난 목표 변경은 다시 결정받는다.
8. 실행기 재시작은 저장된 업무와 원래 요청을 복구한다. 웹 GET·페이지 새로고침·3D 재생으로 실행이나 장부 전이를 발생시키지 않는다. 다중 writer를 기존 SQLite/WriterLease에 몰래 추가하지 않는다.

## 승인과 완료

Harbor 사용자의 업무 확정과 ROSY의 실행 승인은 소유자가 다르다. 승인된 정책 범위에서는 추가 사람 클릭 없이 진행할 수 있어야 한다. ROSY가 별도 검토를 요구하면 Harbor가 해당 대기 상태·이유를 표시하고 그 경계를 우회하지 않는다. 현행 ARM 계약과 정책 승인 결손은 ADR0012를 따른다.

ROSY의 동작 성공·물리 결과와 Harbor의 업무 완료는 각각 판단한다. Harbor는 요구된 최종 배치·다칸 개체 전체·관련 재취급 화물·인증된 근거를 확인한다. 원본 근거가 없으면 완료량을 만들어내지 않는다.

## 분리가 성립했다는 검증

- Harbor의 업무 순서·재취급 규칙 변경이 ROSY 코드 변경을 요구하지 않는다.
- ROSY의 로봇/owner 구현 변경이 지원하는 공개 계약을 유지하면 Harbor 업무 규칙을 바꾸지 않는다. 설치 자원이나 물리 참조 변경은 설치 대응 재검증 대상이다.
- 어댑터 대역으로 Harbor의 정상 진행·부분 완료·불명·취소·재계획·재시작을 시험할 수 있다. 이는 실제 API 호환 검증을 대신하지 않는다.
- 고정된 양 끝 버전의 HTTP 계약 시험에서 인증·idempotency·원본 결속·알 수 없는 응답 거절·승인 대기를 검증한다.
- UI를 닫은 상태에서도 수용된 합성 업무가 단계별로 진행하고, 다시 열면 같은 업무·실행·근거를 읽는다. 실물 수용은 별도다.

## 채택하지 않는 구조

ROSY에 Harbor 전용 재배치 endpoint·항만 workflow를 넣거나, Harbor가 ROSY DB를 읽는 구조는 채택하지 않는다. 화면마다 장치 호출·자동 승인 로직을 두지 않는다. 업무 실행기가 아직 없다는 이유로 브라우저 polling에 업무 진행 책임을 맡기지 않는다. 단순히 HTTP를 사용한다는 이유만으로 의미·상태·데이터 소유가 분리됐다고 보지 않는다.

구체 인터페이스와 전환 순서는 [상세설계24](../design/24-business-execution-boundary.md)를 따른다. 이 결정은 새 ROSY endpoint나 자동 승인 정책을 등록·활성화하지 않는다.
