# ADR 0034: 허용된 범위의 자동 운전과 사람의 예외 개입

날짜: 2026-11-21

상태: **제안(초안), 미수락·자동 실행 미활성**. 사용자 화면 원칙을 실행 정책으로 바꾸기 위한 제안이다.

대체 제안: [ADR0012](0012-user-confirmed-command-dispatch.md)의 매 계획 사용자 확정 원칙, [ADR0025](0025-scenario-import-inbound-decision-rearrangement.md) 결정 3의 입고마다 사람 결정. 수락 전에는 기존 실행 정책이 유효하다. Fleet 승인·admission과 업무 완료 근거는 대체하지 않는다.

## 배경

AI·알고리즘이 정상 업무를 정하고 사람은 진행을 보다가 예외·비상에만 개입한다는 사용자 결정이 있다. 입고마다 결정 버튼을 누르는 현재 흐름과 다르다. 화면에서 버튼을 없애는 일과 실행 권한을 여는 일을 분리해야 한다.

## 결정 제안

1. 사람은 사전에 자동 운전을 허용할 업무·자원·기간·상한을 명시한다. 범위 안의 유효한 계획은 입고마다 사람에게 재결정을 요구하지 않고 실행 후보가 될 수 있다. 구체적인 권한 부여자·상한·저장 방식은 수락 때 정한다. 이 초안은 허용 설정이나 새 토글을 만들지 않는다.
2. 정상 화면은 진행·다음 일·처리할 것을 보여 준다. 운영 역할의 순서·자리 변경·취소는 예외 도구로 둔다. 출처 없는 자동 결정·순서 토글은 비활성이다.
3. 제출 직전의 역할·서비스 신원·설치 binding·계획 버전·야드 신선도·자원 충돌·보유 불명 검사를 유지한다. 범위 만료·변경·실패·결과 불명은 진행을 보류하고 이유를 남긴다. 오래된 계획을 자동 재전송하지 않는다.
4. **Fleet의 승인과 안전 admission은 유지한다.** Harbor는 ROSY 승인·재무장·정지를 대신하지 않고, 직접 장치 명령도 보내지 않는다. 현재 ARM의 별도 기명 승인은 그대로다. 미래 Fleet 정책 변경은 공개 계약과 양 끝 시험을 거쳐 별도로 수용해야 한다.
5. 원래 요청 key·digest·업무와 결과의 결속, 응답 유실 후 원래 key 조회, 물리·업무 완료 근거 검증을 유지한다. 자동 계획·제출·ROSY 실행 종료를 Harbor 업무 완료로 간주하지 않는다.
6. 허용한 사람·시각·범위와 사용된 계획·명령·예외 변경을 추적할 수 있어야 한다. 자동 판단과 기명 사람 확인은 다른 출처로 남긴다.

## 결과와 열지 않는 범위

수락되면 정상 업무의 매건 확정 부담을 줄일 수 있다. 잘못된 허용 범위로 연속 실행이 발생할 위험이 있어 범위 밖 거절·만료·중복 방지·예외 보류 시험이 선행되어야 한다. [ADR0017](0017-rule-governed-rearrangement-decision.md)의 R2 상한과 보류 조건, ADR0025의 시나리오 등록·재배치 조건은 이 초안으로 바꾸지 않는다.

WP01은 문서만 쓴다. `commands.py`·실행기·권한·허용 설정은 수정하지 않는다. 자동 운전 실행은 이 ADR 수락 후 별도 작업이다. 비상 정지는 ROSY 계약 전까지 「ROSY Fleet에서 정지 · 연동 전」으로 끈다.

## 수락 전에 사람이 정할 것

- 허용 부여·철회 역할, 업무·자원 범위, 유효 기간·횟수·이동 상한과 재검토 조건.
- 현재 Fleet 기명 승인 아래에서 자동 제출을 어디까지 허용할지, 별도 플랫폼 계약 변경이 필요한지.
- 정상·만료·범위 밖·중복·통신 유실·낡은 계획·물리 근거 부족 시험과 현장 수용 기준.

화면 계약은 [설계35](../design/35-control-dashboard.md), 권한 목표는 [설계34](../design/34-role-scenario-access-and-menus.md)다.
