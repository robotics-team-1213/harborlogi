# ADR 0029: 업무 HOLD 발생을 장부와 같은 transaction에 outbox로 기록한다

날짜: 2026-11-08

상태: 수락(ROSY D-997 Decision 6의 Harbor 행을 이 저장소의 계약으로 반영). 플랫폼 알림 전달 서비스는 아직 없는 목표이며 이 결정이 그 존재를 가정하지 않는다. 배포·실제 채널 발송·전환은 하지 않는다.

## 배경

D-997은 알림 전달을 여러 앱이 HTTP로 소비하는 독립 공통 서비스로 추출하기로 했고, 첫 전환 생산자를 Fleet 사건 통지와 Harbor 업무 HOLD 통지로 고정했다. Harbor가 담당하는 것은 발생 기록과 발송 직전 유효성이고, 전달·전송 원장은 서비스 쪽이다. 이 저장소에는 outbox도 통지도 없었으므로, 생산자 쪽 계약을 먼저 이 장부 안에 정한다.

## 결정

1. **업무 상태와 알림 outbox를 같은 transaction에 기록한다.** `BusinessLedger`의 모든 비-HOLD → HOLD 전이(명시적 보류, 제출 실패, 대조 중 Fleet HOLD, 재시작 복구)는 같은 SQLite transaction에서 `hold_outbox` 행을 하나 만든다. Django 업무 화면 DB와 분산 transaction을 만들지 않는다.
2. **발생 identity는 `request_key`와 회차 번호다.** polling으로 늘어나는 `row_version`만으로 identity를 만들지 않는다. 같은 HOLD 안의 재조회·같은 원인 갱신은 새 발생을 만들지 않고, HOLD를 벗어났다 다시 들어갈 때만 다음 회차가 된다. 재시작·복원에서 회차와 미해결 outbox 행은 그대로 보존된다.
3. **본문은 최소·불투명 필드만 담는다.** 개입 필요 분류, 무작위 발생 식별자(`notification_id`), 발생 시각, 만료, token 없는 보호 업무 화면 링크뿐이다. 원래 업무 `request_key`는 링크를 포함해 어느 채널 필드에도 나가지 않으며, 업무 키의 짧은 해시 참조도 무솔트 해시는 검색으로 되돌릴 수 있어 넣지 않는다. 업무 구분은 링크가 가리키는 보호 화면에서 한다. 링크 base는 배치 설정으로 HTTPS 보호 화면만 허용한다(원격 운영자가 로그인으로 여는 화면이므로 loopback HTTP는 거부). 그 보호 화면이 `notification_id`를 해석하는 경로는 후속 작업이고, 지금 해석을 지원하는 곳은 같은 PC의 읽기 전용 워크벤치뿐이다. query·credentials·fragment는 허용하지 않는다.
4. **발송 직전 유효성은 Harbor가 확인한다.** 각 (발생, 채널) 전송 시도 직전에 같은 업무·같은 회차가 여전히 HOLD인지, 만료되지 않았는지, 채널이 승인된 수신 범위 안인지 검사한다. 통지 만료는 기본 1시간(설정 가능)이며 Fleet D-661의 숫자를 근거 없이 베끼지 않는다. HOLD가 끝난 뒤의 대기 통지는 거절로 종결하고, 이미 최종 상태인 채널 행은 다시 검사·갱신하지 않는다.
5. **발송 상태는 (발생, 채널) 단위이고 전송은 잠금 밖에서 한다.** 한 번의 시도는 짧은 transaction으로 SENDING을 커밋하고, SQLite 쓰기 잠금을 쥐지 않은 채 전송하고, 짧은 transaction으로 결과를 기록한다. 확실한 연결 전 실패만 PENDING으로 60초 간격을 두고 만료까지 재시도하며, timeout·분류할 수 없는 실패는 UNKNOWN으로 자동 재전송하지 않는다. SENDING 정리는 발송 루프 시작 시 명시적으로 한 번 호출하고(`settle_interrupted`) 읽기·시험 헬퍼는 아무것도 쓰지 않으며, 결과 기록이 대상을 놓치면(다른 시작이 먼저 종결한 경우) 그 시도는 발송 완료로 세지 않는다. 장수 프로세스에서 남의 SENDING은 `interrupted()` 관찰로만 드러나고 자동 재전송은 하지 않는다. 대기 판정은 설정된 채널 중 최종 상태가 아닌 채널이 하나라도 있으면 되고, 한 채널의 최종 상태가 다른 채널의 미시도·재시도를 가리지 않는다. 이 표가 처음 main에 들어가므로 병합 전 초안 표 모양으로의 마이그레이션은 제공하지 않는다(main 스키마에서의 `hold_sequence` 추가 마이그레이션만 있다).
6. **승인 수신 채널이 없으면 외부 발송은 꺼져 있다(기본).** 로컬 HOLD와 outbox는 그대로 유지되고, 실제 전달 서비스 호출 클라이언트가 설정되지 않으면 발송 기능은 비활성이다. 완료 통지, 개인 연락처 자동 등록, 자동 재개, 채팅 승인, 장치 명령은 만들지 않는다.

## 대안

| 대안 | 판단 |
|---|---|
| `row_version` 변화를 알림 identity로 쓴다 | 같은 HOLD를 다시 읽을 때마다 새 알림이 생긴다. D-997이 명시적으로 금지하는 방식이라 채택하지 않는다 |
| Django 업무 화면 DB에 outbox를 둔다 | 업무 장부와 화면 DB 사이에 분산 transaction이 필요해진다. 채택하지 않는다 |
| 지금 바로 외부 채널로 발송한다 | 승인된 전달 서비스·채널이 없고 수신 범위 검사가 없다. 발생 기록과 유효성 계약을 먼저 세우고 발송은 꺼둔다 |
| 전체 발송을 하나의 transaction에 묶는다 | 한 행의 실패가 앞선 행의 SENT 표시까지 되돌려 다음 호출에 중복 발송을 만들고, 네트워크 호출 중 쓰기 잠금을 쥔다. 시도 단위 상태와 잠금 밖 전송으로 대신한다 |

## 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| ADR0005 | 업무 장부가 상태·증거의 정본임을 유지한다. outbox는 그 장부의 같은 transaction에 산다 |
| ADR0013·0015 | 업무 실행 독립과 서비스 신원을 그대로 둔다. 통지 발송은 사람 자격을 쓰지 않는다 |
| ADR0021·0028 | 배치·책임 경계를 바꾸지 않는다. 화면 링크의 base만 배치 설정으로 받는다 |
| ROSY D-661 | Fleet 알림의 예산·UNKNOWN·비노출 계약을 베끼지 않고 Harbor 회차에 맞는 만료를 정한다 |
| ROSY D-997 | 이 결정은 그 Decision 6 Harbor 행의 생산자 쪽 구현이다. 전달 서비스·전환은 플랫폼 쪽 별도 변경이다 |

## 결과와 검증

`harbor/hold_notify.py`(outbox·전달 시도 스키마, 불투명 본문, 발송 직전 검사, 시도 단위 발송 문과 명시적 SENDING 정리)와 `harbor/workflow.py`(같은 transaction 기록), `harbor/ledger.py`(링크의 불투명 식별자로 업무 행 조회)가 바뀌었고, `tests/test_hold_notify.py`가 같은 HOLD polling 무발송, HOLD 종료 뒤 대기 통지 거절, 재진입 새 회차, outbox 원자성, 재시작 보존, main 스키마(hold_sequence 없는 business) 마이그레이션, refresh·대조의 HOLD 진입, 본문 불투명 필드와 키 비노출, 링크 식별자 조회, 미설정 발송 꺼짐, 회차별 단일 발송, 채널 최종 상태가 다른 채널의 미시도·재시도를 가리거나 덮지 않음, 이후 실패의 앞선 발송 재발송 없음, 재시도 간격 준수, 채널별 timeout UNKNOWN, 분류 불능 실패 UNKNOWN, SENDING 잔존의 관찰·명시적 정리·미인정, 전송 중 다른 발송 루프 시작 시 미인정·UNKNOWN, 만료 거절, 채널 수신 범위를 검증한다. 실제 전달 서비스 연결·채널 발송·운영 배포는 이 결정의 범위 밖이며 미래의 플랫폼 전달 서비스 수용 때 별도로 검증한다.
