# ADR 0021: Harbor는 통합관제 R과 같은 운영 PC에서 Compose로 돈다

날짜: 2026-11-04

상태: 수락(2026-11-04, 사용자 결정 "R과 같은 운영 PC", "Docker Compose"). 배치와 설치 형태를 정하는 결정이다.

**2026-11-06 개정(사용자 결정 "하버는 이제 여기에서 돌리지 않는다", "CI/CD로"):** 이 개정이 아래 본문보다 우선한다.
- robttt의 Harbor를 제거했다. R 전용 PC가 준비될 때까지 모델 PC에 임시로 둔다. 아래 대안 표에서 모델 PC를 제외한 이유(학습 부하, 잦은 재시작)는 그대로 남아 있으므로, 이 배치는 임시다.
- R과 다른 PC가 되어 §1의 "R 옆"과 site 방화벽용 host network 덮어쓰기는 임시 배치에 적용하지 않는다. Harbor의 Fleet 상대가 R 하나라는 결정(ADR0018)은 바뀌지 않는다.
- §4의 "고정 커밋 설치"는 CI가 만든 이미지를 digest로 받는 방식으로 바꾼다. 순서(실행기 정지 → 짝 백업 → migrate → 재기동)는 같다. 절차는 [Compose 설치 구성](../../deploy/compose/README.md#갱신)에 있다.
- 사이트 스택과 달리 수동 서명을 두지 않는다. Harbor는 장치 권한이 없고 R을 거쳐서만 동작한다.

이전 상태 기록:
- 구현됨: [Compose 설치 구성](../../deploy/compose/README.md)(이미지·`harbor`·`proxy`·`manage`·env 예시). R 호스트(robttt)에서 빌드·migrate·TLS·로그인·R 서비스 인증을 확인했다([검증 기록](../validation/2026-11-04-compose-on-r-host.md)).
- 설치: 2026-11-04 사용자 지시로 robttt에 설치했다. 팀 리뷰 전의 PR #23 커밋이며, 병합되면 `main` 커밋으로 다시 설치한다. R 현장 전환은 2026-11-02에 적용됐다. D-960 수용 (b)·(d)는 확인했고, (c) R→CELL-A 정지 요청은 팔 토크 차단 위험 때문에 건너뛰었다.
- 미수용: 팔 작업 위임과 근거·재확인 중계(API v1.353–1.356)는 공개 main에 있고 시뮬레이션에서 확인했다([2026-11-06 기록](../validation/2026-11-06-evidence-through-r.md)). 현장 R과 CELL-A는 그 앞의 이미지로 돌고 있으므로, 갱신과 현장 수용 전까지 현장 팔 작업은 HOLD로 다룬다.
- 잇는 결정: ADR0013(업무 실행 독립)·ADR0015(서비스 신원)·ADR0018(꼭대기 관제 하나), 플랫폼 D-893·D-960·D-965.
- 번호: 병합 시점 `main`의 ADR 번호를 다시 확인한다(0020은 PR #20이 쓴다).

## 배경

ADR0018은 Harbor가 R 하나에만 연결한다고 정했다. 하지만 Harbor 서버가 어느 PC에서 어떤 형태로 도는지는 정하지 않았다. [제품 웹 안내](../product-web.md)는 "Waitress 한 프로세스를 TLS proxy 뒤 loopback에"까지만 적었다.

플랫폼 배치(D-960 §5)는 다음과 같다.
- CELL-A는 팔이 꽂힌 OMX 관제 PC에서 돈다.
- R은 임시로 같은 PC에 있고, 목표는 상시 켜 두는 한가한 전용 PC다.
- 모델 PC는 학습·평가, AI PC는 고정 추론을 맡는다.

Harbor 서버는 웹, 상시 실행기, 웹 DB, 업무 장부로 이루어진다. 실행기는 같은 프로세스 안의 스레드이고, 웹 DB와 업무 장부는 각각 SQLite writer 하나다. GPU는 필요 없다.

## 결정

1. **Harbor는 R과 같은 운영 PC에 둔다.** 지금은 OMX 관제 PC에서 R 옆에 둔다. R이 전용 PC로 옮기면 Harbor도 같은 창에서 함께 옮긴다. Harbor의 유일한 Fleet 상대가 R이므로, 둘을 함께 두면 연결과 장애 범위가 같이 움직인다. 모델 PC와 AI PC에는 두지 않는다.
2. **설치는 Docker Compose로 하고, R·CELL-A와 섞지 않는다.** 아래 다섯 가지를 Harbor 자기 것으로 갖는다(D-893 §3).
   - Compose project 이름 `harbor`
   - 공개 포트(기본 9443. robttt의 443·8443은 rosy-site, 8543은 CELL-A가 쓴다)
   - 데이터 volume
   - TLS 인증서
   - R이 발급한 서비스 principal(ADR0015)

   R의 인증서·DB·계정을 빌려 쓰지 않는다.
3. **프로세스는 하나다.** `harbor` 컨테이너가 Waitress와 상시 실행기를 함께 돌리고(`HARBOR_EXECUTOR_ENABLED=1`), 컨테이너 안 `127.0.0.1:8060`에서만 듣는다. nginx `proxy`는 `harbor`의 네트워크 namespace를 함께 써서 TLS를 끝낸다. 그래서 Waitress를 바깥에 열지 않고, 기존 loopback 규칙과 [nginx 예시](../../deploy/web/nginx.conf.example)를 그대로 쓴다. migrate·계정·백업·복원은 실행기를 켜지 않는 일회성 `manage`로만 한다. 서버는 migrate 전에 시작을 거절한다(기존 `require_profile`).
4. **갱신은 팀 `main`에 병합된 고정 커밋으로만 한다.** 순서는 실행기 정지 → 짝 백업 → migrate → 재기동이다. 백업과 복원은 기존 `backup_product`·`restore_product`를 쓴다.
5. **옮길 때는 계획된 전환을 따른다(D-893 §6).**
   1. 진행 중이거나 결과 불명인 인계를 대조한다.
   2. 멈추고 백업한다.
   3. 새 호스트에 복원한다.
   4. R origin을 새 주소로 바꾼다.

   복원된 DB는 새 제출을 막는다(`DeploymentState.restored_at`). 원래 실행 key 대조 전에는 새 요청으로 재시도하지 않는다. 이전 호스트의 서버를 지운 것을 확인한 뒤 새 호스트를 연다.
6. **바꾸지 않는 것.** Harbor는 R 하나에만 연결한다(ADR0018). 자동 승인, 직접 장치 명령, ROSY DB 읽기는 없다(ADR0013). 팔 작업은 R을 거친 위임·근거 중계가 기준 플랫폼 커밋에 들어가고 D-965 수용 조건이 확인되기 전까지 HOLD다.

## 대안

| 대안 | 판단 |
|---|---|
| 모델 PC·AI PC에 둔다 | 모델 PC는 학습 부하와 재시작이 잦고, AI PC는 고정 추론과 다른 서비스의 I/O가 겹친다. 채택하지 않는다 |
| R과 다른 별도 PC에 둔다 | 팔 PC의 부하는 줄지만, 지금은 남는 상시 PC가 없다. R과 Harbor를 따로 옮겨야 하는 일도 생긴다. 채택하지 않는다 |
| systemd 사용자 유닛 | 실험실 고정 도구와 같은 방식이고 이미지가 필요 없다. 하지만 R 사이트 스택과 같은 방식으로 격리하는 쪽을 사용자가 골랐다. 채택하지 않는다 |
| **R 옆 + Compose + 자기 자원** | 연결 상대와 함께 움직이고, 동거해도 포트·DB·인증서·신원이 섞이지 않는다. **채택** |

## 검증

이 결정의 현재 근거와 수용 조건을 나눈다.

- 확인함:
  - Harbor `tools.check_all`
  - `compose.yaml`을 YAML로 읽어 병합 결과를 확인했다. 실행기 스위치는 `harbor`에만 있고 `manage`에는 없다.
- 확인 못 함: `docker compose config`, 이미지 빌드, 컨테이너 기동, 프록시 TLS. 이 노트북에는 Docker가 없다.
- 현장 수용 조건(모두 실제 실행으로 확인되어야 한다):
  1. R 호스트에서 이미지를 빌드하고, migrate 전 시작 거절과 migrate 뒤 기동을 확인한다.
  2. 브라우저에서 Harbor TLS로 로그인한다.
  3. R이 발급한 principal로 연결 검사가 통과한다.
  4. 백업 → 새 volume 복원 → 새 제출 차단이 확인된다.
  5. R과 CELL-A의 포트·DB·인증서가 그대로이다.

팔 작업의 실제 실행은 D-965 수용 조건을 따로 따른다.
