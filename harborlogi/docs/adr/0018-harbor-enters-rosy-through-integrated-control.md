# ADR 0018: Harbor는 ROSY 계층의 꼭대기 관제 하나로 들어간다

날짜: 2026-11-03

상태: 수락(2026-11-03, 사용자 결정 "권장으로 처리"). 연결 대상과 책임을 정하는 결정이다.
- 구현 변경 없음: Harbor의 연결 설정(`FleetConnection`·`HARBOR_FLEET_ORIGIN`)은 이미 origin 하나다.
- 구현 전: 통합관제가 팔 작업을 셀 관제로 넘기는 위임 경로(플랫폼). 아래 「현재 공백」.
- 갱신(2026-11-04, [경계 점검](../validation/2026-11-04-rosy-boundary-audit.md)): 플랫폼 main에 팔 작업 위임(D-965, API v1.353–1.355)과 R의 ARM 중계가 들어갔다. 공백 닫힘 조건 1은 충족됐다. R 중계에는 아직 `physical-evidence`·`rechecks`가 없어(v1.359 착지 대기) R을 거치면 업무 근거와 완료 재관측이 되지 않는다. 조건 2(고정 양 끝 HTTP)와 3(Harbor 통합 시험)은 남았다. 아래 본문은 2026-11-03 판단 그대로 둔다.
- 잇는 결정: ADR0005(책임 지도)·ADR0015(서비스 신원), 플랫폼 D-850·D-855·D-960·D-963.

## 배경

플랫폼 D-960(2026-11-02)은 Fleet을 두 층으로 나눴다.
- 셀 관제(지금 CELL-A): 팔이 꽂힌 제어 PC에서 돈다. 팔 A·B·S의 원장·기명 승인·admission·정지·셀 카메라를 소유한다.
- 통합관제 R: 하위 셀의 요약을 모으고 위임·취소·정지 요청만 중계한다. Pinky `rosy_40`·`rosy_41`은 R이 직접 소유한다.

Harbor 문서는 "Fleet HTTP"라고만 적었고, 연결 설정은 origin 하나다. 그런데 Harbor 요청의 주인이 둘로 갈렸다. 이송(TRIP)은 R, 팔 작업(cell-app compile·proposal, 중립 ARM)은 셀이다.

## 결정

1. **Harbor는 계층의 꼭대기 관제 하나에만 연결한다.** 현장에서는 통합관제 R이다. 셀 관제를 직접 가리키지 않는다.
   - 셀이 늘어도(R → CELL-B) Harbor 설정은 바뀌지 않는다.
   - 개발·시뮬레이션처럼 한 Fleet이 팔과 Pinky를 함께 소유하면 그 Fleet이 꼭대기다. 지금의 하네스와 시험은 그대로다.
2. **요청마다 주인이 다르다. Harbor는 주인을 고르지 않는다.**

   | Harbor 요청 | 실제 주인 | 승인하는 곳 |
   |---|---|---|
   | 이송(TRIP) | R (Pinky 직접 소유) | R |
   | 팔 작업(cell-app·ARM) | 셀 관제 | 셀 화면의 기명 운영자. R은 위임만 한다 |
   | 조회·receipt | 각 주인. R은 요약만 | – |

3. **장치는 Harbor가 모른다.** USB에 무엇이 꽂혔는지, 어느 보드가 팔 A인지, 카메라 역할이 무엇인지는 셀 제어 PC와 셀 Fleet 승인(D-963) 소관이다. Harbor는 설치 binding의 팔 이름(A·B)과 공정 참조만 쓴다.
4. **바꾸지 않는 것.** ADR0015의 서비스 신원은 연결한 꼭대기 관제가 발급한다. 자동 승인 없음, Fleet HTTP만 사용, ADR0005의 업무 완료 3요소는 그대로다.

## 현재 공백

플랫폼 D-855의 위임 wire(`ControlNavigationCandidate`: `robot_id`·`goal`)는 주행 후보만 실어 나른다. 팔 작업을 R에서 셀로 넘기는 위임 종류는 없다.
- 그동안 Harbor는 R을 통한 팔 작업에 실행 경로가 있다고 표시하지 않는다.
- R이 자기 소유가 아닌 작업셀의 팔 제안에 어떻게 응답하는지는 확인하지 않았다. 응답이 거절이거나 불명확하면 기존 규칙([execution.md](../execution.md))대로 HOLD하고 자동으로 다시 보내지 않는다.
- 셀 관제로 직접 연결을 바꿔 공백을 메우지 않는다. 그러면 이송의 주인(R)을 잃는다.

공백이 닫히는 조건은 다음 셋이다.
1. 플랫폼이 팔 작업 위임 종류를 공개 계약에 더한다.
2. 고정된 양 끝 Fleet HTTP에서 R 제안 → 셀 inbox → 셀 승인 → R 조회가 확인된다.
3. Harbor 통합 시험이 그 경로로 돈다.

### 진행 (2026-11-03)

| 조건 | 상태 |
|---|---|
| 1 위임 종류 | 플랫폼 API v1.353–v1.355가 공개 `origin/main`(`ed455ea`)에 있음. v1.356은 이 시험 범위 밖 |
| 2 양 끝 HTTP | 플랫폼 시험에서 실제 Fleet 앱 둘(R·셀)로 확인 |
| 3 Harbor 통합 시험 | 공개 SHA `ed455ea`로 모델 PC에서 `--arm-via-r` 11/11, 기본·`--full-flow` 통과(2026-11-04). 게시 전 SHA에서는 17/18(1회 HOLD, 원인 미확인). [검증 기록](../validation/2026-11-03-arm-via-integrated-control.md) |

R은 증거·recheck도 셀의 관제 단위 API로 전달하고, 셀 운영자 화면에 요청한 앱(`delegated_by`)을 보여 준다. 조건 2·3은 시험 PC에서 충족됐다. R 중계의 `physical-evidence`·`rechecks`는 API v1.356으로 공개 main에 들어갔고 `--arm-via-r`로 확인했다([2026-11-06 기록](../validation/2026-11-06-evidence-through-r.md)). 남은 것은 현장 R·CELL-A 갱신과 현장 수용이다. 현장 R↔CELL-A 연결은 플랫폼 D-960 수용 조건으로 남는다.

## 대안

| 대안 | 판단 |
|---|---|
| Harbor가 R과 각 셀에 따로 연결 | 플랫폼 변경 없이 바로 된다. 대신 Harbor가 셀 구성을 알아야 하고 셀이 늘 때마다 설정과 신원이 는다. 채택하지 않는다 |
| Harbor가 셀 관제 하나에만 연결 | Pinky 이송의 주인이 R이라 이송을 잃는다. 채택하지 않는다 |
| **꼭대기 관제 하나 + 위임** | D-960 계층과 맞고 Harbor 설정이 고정된다. 위임 경로가 생길 때까지 팔 작업은 HOLD다. **채택** |
