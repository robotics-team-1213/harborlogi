# ADR 0019: 컨테이너마다 사건 이력을 기존 기록에서 모아 보여 준다

날짜: 2026-11-04

상태: 수락(2026-11-04, 사용자 결정 "adr로 결정하고 처리"). 1단계를 구현했다.
- 구현됨: 화물별 이력 화면 `/cargo/<id>/history/`(`harbor_web/cargo_history.py`), 관측 기준 체류, 화물 목록의 「이력 보기」.
- 구현 전: 선사(화주)별 보기, 처리 실적 지표, 실시간 갱신. 아래 「다음 단계」.
- 잇는 결정: ADR0005(위치 두 층)·ADR0013(업무 실행과 플랫폼 분리)·ADR0018(R 하나로 연결).

## 배경

Harbor의 운영 현황은 고른 관측 한 장의 스냅샷이다. 재고·점유·예상 이동은 보이지만, 컨테이너 하나가 언제 들어와 어디에 있었고 몇 번 재취급됐는지는 여러 화면에 흩어져 있다.

터미널 운영 시스템의 대시보드는 보통 선박·야드·게이트로 나뉘고 체류 시간·재취급·장비 유휴를 본다. 선사는 컨테이너별 사건(양하·적하·게이트 반입·반출)을 받는다(DCSA Track & Trace). 두 쪽 모두 바탕은 컨테이너별 사건 이력이다.

## 결정

1. **컨테이너별 사건 이력을 기존 기록에서 모은다. 새 표를 만들지 않는다.**
   - 출처: 화물 등록, 업무 요청, 계획(다른 화물 계획의 재취급 대상 포함), 실행 지시, ROSY 공개 조회 사실(`CommandFact`), 업무 근거 제출, 현장 확인, 출발 의도, 관측.
   - 각 줄은 출처 기록을 밝힌다. 사건을 합성하거나 업무 완료를 추정하지 않는다.
   - 기록이 이미 불변이고 감사되므로, 같은 사실을 두 번 저장하는 표는 어긋날 위험만 더한다.
2. **체류는 관측 기준으로만 센다.** 이 화물이 나타난 첫 관측과 마지막 관측의 차이다. 관측 사이의 반입·반출 시각을 추정하지 않는다. 해석할 수 없는 관측은 건수만 밝히고 제외한다.
3. **ROSY 작업 상태·receipt는 실행 결과로만 보인다.** 업무 완료는 기존처럼 업무 장부의 근거 대조로만 판단한다(ADR0013).
4. **장비 상태는 Harbor가 만들지 않는다.** 실시간 로봇·팔 상태는 ROSY 통합관제 R의 요약이 정본이고, Harbor는 기존처럼 연결만 둔다(ADR0018).

## 다음 단계

| 단계 | 필요한 것 |
|---|---|
| 선사(화주)별 보기 | 화물의 선사 식별(현재 `Cargo`에 없음)과 선사별 접근 권한. 외부 공개라면 DCSA 사건 모양 대응 |
| 처리 실적(완료량·시간당 물동량) | 완료량은 ADR0020 결정 6으로 연결했다. 시간당 물동량은 집계 시간 기준이 정해질 때까지 계획 수치를 실적으로 바꾸지 않는다(운영 현황의 「미집계」 유지) |
| 실시간 갱신·경보 | 관측·ROSY 사건의 푸시 또는 주기 조회와 그 출처·신선도 표시 |
| 이력 규모 | 1단계는 최근 관측·계획 200건만 훑는다(코드의 `shortcut`). 이력이 그보다 커지면 화물별 색인을 둔다 |

## 대안

| 대안 | 판단 |
|---|---|
| 사건 표를 새로 두고 각 기록 시점에 쓴다 | 표준 사건 모양을 바로 만들 수 있다. 대신 모든 쓰기 경로를 바꿔야 하고 원래 기록과 어긋날 수 있다. 1단계에는 채택하지 않는다 |
| 운영 현황 화면에 지표만 더한다 | 컨테이너 하나의 흐름을 보여 주지 못하고 실적 미집계 원칙과 부딪힌다. 채택하지 않는다 |
| **기존 기록에서 읽어 모은다** | 쓰기 경로를 바꾸지 않고 출처를 그대로 보여 준다. **채택** |
