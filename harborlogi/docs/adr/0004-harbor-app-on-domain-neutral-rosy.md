# 0004 — 도메인 중립 ROSY 위의 항만 앱 — 자원 배정과 인계 근거

Status: Proposed(제안). 2026-10-21 작성, 2026-10-23 갱신. 2026-10-24 설계 저장소 rosy-docs에서 이전했다(출처: rosy-docs `1b3d80cee73c3bc2d826554fd4f3b06f3d7b1666`의 `ADR/ADR-07 도메인 중립 ROSY 위의 항만 앱 — 자원 배정과 인계 근거.md`). 이전 뒤 정본은 이 문서다. 번호만 바꾸고 결정 내용은 바꾸지 않았다.

도메인 중립 ROSY 위에 업무 앱을 올리는 방향과 암 2+1·Pinky 3대·충전 한 자리 구성은 사용자와 논의했다. 공개 계약의 세부 필드·코드 공통화·자동 충전·병렬 주행·실물 수용을 이 문서로 승인하지 않는다.

## 배경

이번 항만 문제는 회수 전 운송 작업계획 변경으로 회수 순위가 바뀌어 매몰 화물을 꺼내야 할 때, 추가 취급과 출고 준비 지연을 줄이는 것이다. 요구가 전혀 미정이라는 전제로 구현 준비를 미루지 않는다. 문제 선택과 UR/SR 전체 채택, 해결 전략의 우월성·실물 가능성은 구분한다.

기존 Vault(rosy-vault, 2026-10-24 은퇴)는 `core/jobs.py`의 입고·출고·보관 칸 모델, 동기 `StepPort`, 한 번에 한 작업을 실행하는 보수적 경로를 갖는다. Fleet 어댑터는 집기를 놓기와 합쳐 실행하며 집기 단계에서 실제 동작 전 유예 성공을 돌려준다. 이 의미를 항만의 화물 보유·차량 출발 허용으로 재사용하면 안 된다. 기존 보관고 동작은 보존하면서 공통 실행 계약을 별도로 대조해야 한다.

플랫폼 쪽에는 D-827(플랫폼·공정·앱), D-828(접수·물리 완료·근거), D-829(업무 제약·자원 배정)의 Proposed 초안을 같은 작업에서 작성한다. 이 문서는 내부 장비 구성과 항만 적용을 소유하며 플랫폼 ADR에 팀 내부 설계를 복제하지 않는다.

## 결정 제안

| 번호 | 결정 | 확인 방법 |
|---|---|---|
| A1 | 항만 앱은 컨테이너·슬롯·적층 관계·회수 그룹/순위·변경 지시 버전·처리 전략·업무 장부·화면을 소유한다 | 회수 순위나 전략만 바꾸는 시험에서 플랫폼 코드 변경 없음 |
| A2 | ROSY는 공통 작업·관측·실행 근거·장치/자원 가용성·admission을 담당하고 장치 owner는 실행·정지를 집행한다 | 앱의 내부 플랫폼 import·DB 쓰기·ROS 직접 연결 없음. 기존 권한 시험 보존 |
| A3 | 앱은 목표와 후보·제약을 요청하고 플랫폼은 지원되는 범위에서 실제 자원을 배정한다. 앱이 A/B·S 등 허용 후보를 지정할 수 있으나 가용성·권한을 우회하지 않는다 | 불가용 후보·역할 불일치·점유 불명·오래된 관측을 거절하거나 보류 |
| A4 | 암 S 1대는 공급·회수, 암 A/B 2대는 야드 적층·반출·필요한 협응을 맡는다. 모든 작업을 양팔 공동 접촉으로 만들지 않는다 | 역할·도달/퇴피 조건을 배치로 설정. S 경합과 A/B 독립/협응 시간을 따로 측정 |
| A5 | Pinky 3대는 공동 운송 풀이다. 운송·다음 작업 준비·대기/충전 교대는 작업에 따라 바뀌고 차량 번호에 고정하지 않는다 | 같은 업무 입력에서 가용 차량을 바꿔도 업무 정책 코드 변경 없음 |
| A6 | 충전소는 한 자리로 계획한다. 자동 도킹·충전 시작은 미확인이고 초기 운용은 수동 교대를 지원한다 | 충전 자리 점유·대기·정비 차단을 구분. 도착만으로 충전 상태를 기록하지 않음 |
| A7 | 관측 위치와 계획 위치, 작업 담당과 물리적 화물 보유, 명령 접수와 완료, 빈 차 출발 허용과 목표 안착을 구분한다 | 작업·시도·계획 버전·관측 근거를 연결하고 단계별 실패 시험으로 확인 |
| A8 | 첫 흐름은 회수 시작 전 변경 접수 → 방해 화물 처리 → 목표 운송 → S 하역 → 방해 화물 정리·팔 퇴피다 | 목표 도착만으로 완료하지 않음. 완료 시 관련 화물 위치·보유·팔 퇴피 근거가 유효 |

| A10 | 항만 업무 모듈은 기존 Vault의 입고·출고 장부에 억지로 끼우지 않는다. 후속 구현은 ROSY 밖의 별도 앱으로 한다. 이름은 DL-18(제안, 2026-10-23)에 따라 프로젝트 HarborLogi, 앱 Harbor, 플랫폼 ROSY로 부르고 앱 이름에 ROSY를 넣지 않는다. DL-22(2026-10-24, DL-19·DL-20 보완)에 따라 코드·실행 계약의 정본은 팀 `robotics-team-1213/harborlogi`의 `harborlogi/`이며, 팀 main의 확정 변경을 과정 `kernel-robot-8th/kernel-robot-repo-2`에 제출 PR로 반영한다. 처음 작성한 `rosy-port`(2026-10-24 은퇴)는 보관했다 | 현재 변경에서 새 저장소·서비스·DB 생성 없음. 기존 보관고 회귀와 데이터 보존 |

## 기존 결정과의 관계

ADR-02~06은 비공개 설계 저장소 rosy-docs의 ADR 번호다.

| 결정 | 관계 |
|---|---|
| ADR-02 | 도메인 규칙을 앱에 두고 연결 지점을 제한하는 원칙 유지. 보관고 공통화는 함수 이름이 아닌 실제 의미·실패 동작으로 판단 |
| ADR-03 | 역할과 실행자의 물리 배치를 분리하고 실제 장치 identity는 설정으로 연결 |
| ADR-04·05 | 현재 direct/fleet 허용 환경·실물 승인·이동 한정 재시도·시뮬 자동화 경계를 유지. 변경 시 별도 ADR 필요 |
| ADR-06 | S/A/B·Pinky·인계의 기준을 재사용. 제한 공유나 양팔 방식을 이미 우월한 해법으로 확정하지 않음 |
| 플랫폼 D-827~829 | 공통 책임·결과 의미·자원 배정의 제안 기준. 플랫폼 API와 양 끝 구현이 갖춰져야 실제 소비 가능 |

## 대안

- Vault 전체를 범용 프레임워크로 변경: 입고·출고·칸 모델과 동기 실행 가정을 항만에 전파하고 기존 앱의 회귀 범위를 키워 채택하지 않는다.
- 항만 앱이 장치·충전·공통 원장을 전부 재구현: 현재 direct 시연 경로는 호환 대상으로 보존하되 장기 구조로 복제하지 않는다.
- 장비 수에 맞춰 Pinky 역할을 영구 고정: 운송 수요와 충전 상태에 따라 유휴/병목이 생길 수 있어 채택하지 않는다.
- 자동 충전·다대 병렬 운행을 첫 흐름의 전제로 사용: 현재 실측·수용 근거가 없으므로 보류한다.

## 영향과 후속 작업

앱은 화물의 업무 상태를 소유하지만 물리 보유·점유·작업 성공을 추측하지 않는다. 플랫폼의 미지원 기능이 발견되면 기존 direct 경로를 조용히 확장하지 않고 플랫폼 소유자의 별도 계약 변경으로 요청한다.

분할 구현과 검증 기준은 [항만 앱 분할 실행계획](../plans/2026-10-21-harbor-app-split.md)을 따른다. 단계는 업무 모델·순수 정책, 배치·제약, 어댑터·결과 처리, 충전 교대, 통합 흐름으로 나눈다.
