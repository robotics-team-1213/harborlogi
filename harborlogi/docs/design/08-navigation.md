# Harbor 정보 구조와 네비게이션

상태: 기존 조회 preview의 디자인 기준과 탐색 기록. **조치 필요 중심의 PC 첫 화면은 사용자 확정**이다. 계정/영속 입력을 가진 새 제품 웹의 경로·역할·탐색 정본은 [제품 웹 계약](13-product-web-surface.md)이다. 아래 `/overview`, `/work`, `/planning`, `/help`는 8050 조회 preview에 한정되며 새 제품 경로와 혼용하지 않는다. Harbor 화면 URL은 ROSY API 계약이 아니다. 원칙은 [디자인 철학](07-design-foundation.md)을 따른다.

## 1. 탐색을 세 층으로 구분한다

```text
앱 전체 탐색       운영 현황 / 업무 / 재고 / 장비 / 기록
업무 목록 맥락     검색 / 상태 필터 / 조치 필요 보기 / 선택한 업무
한 업무 안의 탐색  개요 / 계획 / 실행·근거 / 기록
```

전역 메뉴는 ‘어떤 정보를 보러 왔는가’, 목록은 ‘어떤 업무인가’, 업무 탭은 ‘이 업무의 어떤 판단인가’에 답한다. 지금의 작업 목록을 전역 메뉴로 부르거나, 상태 필터마다 별도 제품 영역을 만들지 않는다.

## 2. 전역 메뉴

| 메뉴 | 사용자 질문·핵심 내용 | 상세로 연결하는 기준 |
|---|---|---|
| **운영 현황** | 지금 누가 무엇을 확인해야 하나? 조치 필요 업무와 이유·책임·확인 시각 | 같은 업무 목록의 필터 또는 원래 업무 ID |
| **업무** | 내가 찾는 업무는 어디까지 진행됐나? 검색·계획/진행/보류/최종 근거/완료 보기 | 업무 ID. 계획과 실행마다 새 업무 상세를 만들지 않음 |
| **재고** | 이 화물은 어디에 있고 무엇을 옮겨야 하나? 관측 위치·적층·임시 위치·출처/시각 | 화물 ID→관련 업무 또는 새 계획의 입력. 드래그로 실제 재고 변경 없음 |
| **장비** | 어떤 자원 때문에 이 업무가 막혔나? 장비 역할·가용성·출처와 영향 업무 | 자원 참조→관련 업무, 필요하면 Fleet로 인계. 장치 조종판 없음 |
| **기록** | 누가 어떤 기준과 근거로 판단했나? 업무별 변경·연결 실패·대조·사용자 감사 | 원래 업무·계획 revision·mission 참조 |

환경·연결 상태, 도움말, 사용자/권한, 설정은 상단 또는 전역 메뉴 하단의 보조 영역이다. 실제 단일 사이트 구성에 아직 없는 사이트 선택기나 사용자 메뉴를 꾸며 넣지 않는다. 설정은 실제 권한 정책과 기능이 준비된 역할에만 노출한다.

### 현재 제품 웹의 역할 시나리오 메뉴

위 표는 초기 preview 정보 구조의 기록이며 지우지 않는다. 제품 웹의 실제 메뉴는 담당자의 일 순서로 묶은 아래 구성이다. 정본은 [34 역할별 시나리오 접근과 메뉴](34-role-scenario-access-and-menus.md)와 [13 계정·역할](13-accounts-and-roles.md)이며, 코드의 기준은 `harbor_web/access.py`다.

| 묶음 | 항목(경로) | 보이는 역할 |
|---|---|---|
| 업무 처리 | 운영 현황(`/`), 반출 관제(`/outbound/`), 화물·요청(`/requests/`), 실행·대조(`/work/`), 자동 재배치(`/rearrangement/`) | 조회·업무 담당·관리 |
| 재고·근거 | 재고·관측(`/inventory/`), 기록·검증(`/records/`) | 조회·업무 담당·관리 |
| 현장 | 현장 확인(`/field/`) | 업무 담당·현장 확인·관리 |
| 관리 | 설정·계정(`/settings/`) | 관리 |
| 도움말 | 업무 안내(`/workflow/`) | 모든 역할 |

- 보일 항목이 없는 묶음은 이름도 숨긴다. 메뉴에 없는 등록·편집 화면(화물 등록, 요청 등록 등)은 각 영역 안에서 열고 역할별로 서버가 검사한다.
- 묶음 이름 아래에 가는 구분선을 둔다. compact rail에서는 묶음 이름을 시각적으로 숨기되 보조 기술에는 남기고, 구분선과 항목 아이콘은 유지한다.
- 900px 이하에서는 메뉴를 펼쳤을 때 묶음마다 이름 아래에 항목을 두 열로 배치한다.
- topbar의 현재 위치 이름(crumb)은 같은 `access.py` 항목의 이름에서 가져와 메뉴와 어긋나지 않는다.
- 사이드바 하단에는 보유한 역할의 담당 이름을 보여 주고 역할이 없으면 "역할 미배정"이다. compact rail에서는 이 하단 영역을 숨긴다.

### 별도 전역 메뉴로 만들지 않을 것

- **확인 필요:** 운영 현황의 중심이자 업무 목록의 저장된 보기다. 업무 원장을 복제하는 별도 큐를 만들지 않는다.
- **계획:** 업무의 한 단계이며 업무 상세의 계획 탭이다. 화물 선택은 재고에서도 시작할 수 있지만 생성 후 같은 업무로 모인다.
- **ROSY:** 외부 앱으로 연결하는 명시적 인계다. Harbor 내부 메뉴처럼 보이거나 같은 세션·승인을 공유한다고 표시하지 않는다.
- **완료/오류:** 업무 목록의 상태 필터다. 별도 정보 구조와 상세 경로를 만들지 않는다.

## 3. 첫 화면: 조치 필요 중심 운영 현황

가장 먼저 **조치가 필요한 업무**를 이유별로 보여 준다. 추천 분류는 ‘접수 결과 대조 필요’, ‘업무 근거 부족’, ‘보류’, ‘조회/연결 문제’다. 실제 판정이 가능한 항목만 만든다. `WAITING` 전체를 오류나 조치 필요로 분류하지 않는다.

각 항목은 업무/화물, 알려진 막힘, 책임 역할, 허용된 다음 행동, 정보 시각을 담는다. 책임 인원이 아직 없으면 ‘담당 미지정’으로 표시한다. Fleet 이유가 없으면 추측한 고장명을 넣지 않는다.

순서는 확인된 위험/긴급도, 명시된 업무 우선순위, 안정적인 업무 ID를 기준으로 설계한다. 아직 위험도·마감·대기 시작 시각이 공급되지 않으면 그 순위나 경과 시간을 만들지 않는다. 초기 구현은 판정 가능한 분류와 안정적인 정렬만 사용한다.

하단에는 진행 중 업무로 이동하는 링크와 데이터 상태를 둔다. 근거 없는 전체 효율·진행률·‘정상 로봇 수’를 첫 화면의 대표 지표로 두지 않는다.

**건수 규칙:** 사용자에게 허용된 업무 단위로 센다. 단계·Action·관측 수를 업무 수와 합산하지 않는다. 조회 실패·일부 미지원이면 ‘미확인/부분 조회’를 표시하며 0건으로 바꾸지 않는다. 서로 겹치는 분류의 합을 전체 업무 수처럼 표시하지 않는다.

## 4. 업무 목록과 상세

목록은 ‘전체 / 계획 / 진행 / 보류 / 최종 근거 / 완료’의 보기와 검색을 갖는다. backend 상태를 새 persisted enum으로 바꾸지 않고 UI 보기와 대응시킨다. `SUBMITTING`은 ‘접수 결과 확인 필요’, `WAITING`은 내부 실행 상태에 따라 설명하며 임의 성공을 표시하지 않는다.

상세의 공통 머리에는 업무·화물·현재 상태·막힌 이유·다음 행동을 유지한다. 그 아래 탭을 둔다.

| 탭 | 책임 |
|---|---|
| 개요 | 현재 판단, 알려진 위치, 단계, 업무별 다음 행동 |
| 계획 | 이동 순서·주/대체 팔·임시 위치 이유·계획 revision과 binding |
| 실행·근거 | Fleet job/Action, physical receipt, Harbor 업무 근거를 서로 다른 섹션으로 대조 |
| 기록 | 이 업무의 계획/판정/제안/대조/사용자 기록. 전역 기록의 업무 필터와 같은 원본 |

새 tab이 없는 정보를 채워 주지는 않는다. 예를 들어 현 장부에는 완전한 사용자 감사가 없다. 기록 탭을 완성된 감사 화면처럼 열지 않는다. current mission이 없는 최종 단계는 과거 mission을 현재 실행으로 위장하지 않는다.

## 5. PC와 태블릿의 배치

```text
PC: 1280px 이상 — 다음 구현 기준
┌──────────────── 환경·연결·사용자 보조 영역 ────────────────┐
│ 전역 메뉴 200 │ 업무 목록 280 │ 업무 제목·현재 판단          │
│ 운영 현황     │ 검색/보기     │ 개요 / 계획 / 실행·근거 / 기록 │
│ 업무 / 재고   │ 업무 행       │ 현재 탭의 내용               │
│ 장비 / 기록   │               │                            │
└──────────────────────────────────────────────────────────┘

태블릿: 768~1279px — 목록과 상세는 각각의 화면
┌──── 메뉴 · 현재 영역 · 환경 ────┐   ┌──── 업무 목록으로 ────────┐
│ 조치 필요 또는 배정 업무 목록 │ → │ 같은 업무 제목/판단/탭  │
│ 검색/보기 · 업무 행           │   │ 필요한 확인 한 가지    │
└─────────────────────────────┘   └────────────────────────┘
```

PC에서만 넓이에 따라 목록과 상세를 함께 둔다. 1280px에서도 상세 읽기 폭이 부족한 실제 콘텐츠가 확인되면 목록을 접는 선택을 제공한다. 태블릿은 전역 메뉴 drawer와 목록→상세 이동을 사용하며 PC의 세 열을 좁게 유지하지 않는다. 768px 미만도 한 열로 읽게 한다.

현장 역할의 기본 진입은 향후 ‘배정된 확인’으로 한정한다. 같은 업무 원본을 사용하지만 역할·회차·권한 결속이 갖춰져야 한다. PC와 태블릿의 역할 변경을 CSS 폭만으로 추정하지 않는다. 가로 회전은 배치를 바꿀 뿐 신원과 권한을 바꾸지 않는다.

## 6. 위치·복귀·상태 보존

아래는 Harbor **화면 URL 제안**이며 현재 `/`와 `/api/work`를 변경했다는 뜻이 아니다.

```text
/overview
/work?view=needs-action&q=...
/work/{business_id}
/work/{business_id}/plan
/work/{business_id}/execution
/work/{business_id}/history
/inventory?cargo=...
/equipment
/history?business=...
```

- URL에는 업무 식별과 화면 보기만 넣는다. token·개인 입력·서버 설정·증명 payload는 넣지 않는다. ID가 허용돼도 서버가 scope를 다시 검사한다.
- 현재 전역 메뉴는 `aria-current=page`로, 업무 선택과 현재 탭은 각각의 의미로 표시한다. 같은 화면에서 여러 곳을 동시에 ‘현재 페이지’로 선언하지 않는다.
- 검색·필터·정렬·목록 스크롤은 상세 이동과 browser 뒤로 가기에서 복구한다. 직접 열기는 서버의 현재 접근 권한으로 같은 대상을 읽는다.
- 선택 업무가 필터 밖으로 이동하면 상세를 갑자기 닫지 않고 ‘현재 보기 밖의 업무’를 표시한다. 목록만 새 업무로 자동 선택하지 않는다.
- 메뉴 drawer는 키보드로 열고 닫으며 닫으면 원래 버튼으로 포커스를 돌린다. 탭은 방향키·Home/End, 내용 이동은 Tab을 사용한다. 업무 선택 후 상세 제목으로 포커스를 옮긴다.
- 빈 목록·조회 실패·권한 거절·업무 없음은 다른 화면이다. 실패 시에도 현재 위치와 재시도/목록 복귀 경로를 남긴다.

## 7. ROSY 인계

작업 상세의 ‘Fleet에서 확인’은 별도 앱 이동이다. 원래 mission ID 복사와 설정된 콘솔 열기를 제공하고, 새 탭·별도 로그인을 명시한다. 현재 지원을 확인하지 못한 mission deep link나 승인 성공 callback은 만들지 않는다. 복귀하면 원래 job을 다시 읽고 현재 업무와 대조한다. 현행 조건은 [Fleet 인계 계약](05-fleet-handoff.md)을 따른다.

## 8. 실제 메뉴 개방 순서

토큰·전역 shell과 **장부에서 도출 가능한 운영 현황 + 업무 영역**, 사용 안내를 구현했다. 데이터와 권한이 없는 재고·장비·기록 메뉴를 눌러도 할 일이 없는 빈 화면으로 늘리지 않는다. 나머지 영역은 필요한 조회 계약·source·권한과 화면이 준비된 단계에서 추가한다. 기존 업무 ID 중 점 경로·슬래시·역슬래시가 있는 값은 `/work?key=…&tab=…`로 보존해 직접 열기와 새로고침을 지원한다.

재고·반출 계획은 기존 domain planner를 연결한 demo 기능이다. 실제 모드에서는 메뉴를 숨기고 직접 열어도 source 미설정으로 표시하며 합성 화물 선택을 제공하지 않는다. [제품 흐름과 계획 페이지](11-retrieval-planning-page.md)를 따른다.

제품 웹 메뉴는 이후 역할 시나리오 묶음으로 바뀌었다(§2 "현재 제품 웹의 역할 시나리오 메뉴"). 개방 순서의 위 서술은 그 이전 시점의 기록이며 현재 항목은 `harbor_web/access.py`와 [34](34-role-scenario-access-and-menus.md)를 따른다. 새 메뉴의 브라우저 확인(1440px 펼침·compact rail, 1100px, 메뉴를 연 600px)에서 묶음·구분선이 보이고 가로 넘침이 없음을 확인했다. 현장 태블릿 수용은 하지 않았다.

로컬 브라우저에서 운영 현황→보류 업무→계획→실행·근거→직접 URL/뒤로 가기→원래 보기와 compact drawer를 검사한다. 실제 Fleet의 승인 화면 왕복·운영 로그인·현장 태블릿 수용은 이 데모 브라우저 검증과 구분한다. 새 페이지의 증거는 [검증 기록](../validation/2026-10-25-navigation-pages.md)을 따른다.
