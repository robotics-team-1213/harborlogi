# Harbor UI·UX 상세설계

상태: 전체 화면 구성은 검토안이다. 후속으로 PC-01/04 중심의 [로컬 조회 웹](../web-workbench.md)을 구현·검증했다. 관제 PC 중심 + 현장 태블릿 보조, 브라우저 웹앱은 사용자 확인 사항이다. 아래 전체 구성·조작 문구의 실제 사용자 수용과 운영 기능 개방은 별도다.

## 1. 정보 구조

사용자 확정으로 PC 첫 화면은 **조치 필요 중심**이다. 이후 정리한 [네비게이션 설계](08-navigation.md)를 정보 구조의 정본으로 따른다: 운영 현황 / 업무 / 재고 / 장비 / 기록. 확인 필요는 업무 보기, 계획은 업무 탭, 설정은 보조 영역이다. 아래 화면 ID는 기능 요구를 추적하는 참조이며 모두 별도의 전역 메뉴가 아니다.

**현재 제품 웹:** 전역 메뉴는 담당자의 일 순서에 맞춰 업무 처리 / 재고·근거 / 현장 / 관리 / 도움말 다섯 묶음으로 나뉜다. 각 항목은 역할에 따라 보이며 묶음에 보일 항목이 없으면 묶음 이름도 숨긴다. 메뉴·경로·역할은 `harbor_web/access.py` 한 곳이 정하고, 사이드바 하단에는 역할 코드 대신 담당 이름(업무 담당·현장 확인·설치·운영 관리·조회)을 보여 준다. 항목별 공개 범위와 묶음 설계는 [34 역할별 시나리오 접근과 메뉴](34-role-scenario-access-and-menus.md), 화면 배치는 [08 네비게이션](08-navigation.md)을 따른다. 브라우저 확인은 1440/1100/600px의 메뉴 묶음·구분선·가로 넘침 없음까지이며 현장 태블릿 수용은 하지 않았다.

태블릿 기본 진입은 **내 확인 작업**이다. 전체 계획 편집·장비 제어·설치 설정을 축소판으로 넣지 않는다. PC에서도 같은 확인 화면을 열 수 있지만 실제 현장 확인 권한은 서버가 검사한다.

상단 공통 정보: 현재 사용자와 책임 역할, 사이트 표시명, `simulation/운영 미수용/운영` 환경 상태, 마지막 원본 관측 시각, 연결 상태. “연결됨”과 “업무를 진행할 근거가 신선함”을 같은 표시로 합치지 않는다.

서로 다른 source의 시각을 하나의 최근 시각으로 합쳐 전체가 신선하다고 표시하지 않는다. 요약은 필수 근거의 누락/만료 개수를 보여 주고 상세에서 각 원본 시각을 확인하게 한다.

| TB-01 | 내 확인 작업: 현장에서 볼 대상은 | 차량/공급 인계 회차/화물 식별 정보, 필요한 확인, 유효 시간, 배정, 미확인 이유 | 대상 상세 열기. 확인 전체 일괄 처리 없음 |

## 3. PC 작업 상세 wireframe

아래 값은 합성 예이며 현재 UI의 스크린샷이 아니다.

```text
Harbor   [simulation]   관제 업무 담당   원본 관측 00:00:03 전
업무 > 반출 작업 demo-01             [Fleet 열기] [ID 복사]
──────────────────────────────────────────────────────────
반출 대상 C1 / 장치 칸 Y1 하단 → 반출대
업무: 진행 대기      현재: C2 복귀      계획 기준 rev 12
──────────────────────────────┬───────────────────────────
업무 단계                      │ 현재 단계의 대조
1 C2 → 임시 칸   근거 확인     │ 로봇 동작: 성공
2 C1 → 반출대    근거 확인     │ 물리 receipt: 확인됨
3 C2 → 원위치    근거 대기     │ C2 복귀 위치: 관측 없음
                              │ 관련 팔 퇴피: 확인 대기
관측 재고 / 계획 예상 배치     │ 다음: 관측 담당 확인 필요
각 칸의 단·source·시각         │ [근거 상세] [현재 상태 조회]
──────────────────────────────┴───────────────────────────
[진행·근거] [계획과 기준] [감사] [기술 식별자]
```

`UX-01`: 물리 receipt가 있어도 부족한 업무 근거를 같은 화면에서 보인다. 진행률100%·녹색 전체 완료로 덮지 않는다. `UX-02`: 현재 단계만 조작 대상으로 삼고 이미 끝난 단계의 요청을 다시 보내지 않는다.

재고 칸은 아래→위로 저장되는 모델 순서를 이해할 수 있도록 단 번호와 위에 막고 있는 화물을 표시한다. 화면은 상단 화물을 위에 그리되 모델 저장 순서를 반대로 덮어쓰지 않는다. 좁은 공간에서는 표와 수직 칸 상세를 제공한다.

## 4. 태블릿 현장 확인 wireframe

```text
Harbor · 내 확인 작업     [연결됨] [simulation]
차량 demo-vehicle-01
공급 인계 회차 demo-load-07 · 화물 C1

확인할 내용
S 그리퍼가 이 차량의 적재면에서 빠졌는지 직접 확인
이 기록은 현재 공급 인계 회차에만 사용됩니다.

확인 상태: 아직 기록하지 않음
[직접 확인해 기록]     [확인 불가 신고]

기록 후: “현장 확인이 기록되었습니다. 출발은 별도 조건을 대조합니다.”
```

차량·회차의 식별이 불가능하거나 회차 결속 계약이 준비되지 않았으면 확인 조작을 열지 않는다. 촬영 이미지가 있다면 원본 시각·출처와 함께 보조 자료로 표시하며 현재 눈앞 대상의 확인을 대체하지 않는다. 바코드/QR은 후속 옵션이며 첫 구현의 필수 장비로 가정하지 않는다.

## 5. 상태별 문구와 행동

| 상황 | 표시와 행동 |
|---|---|
| 첫 사용 / 등록 자원 없음 | 설치·binding/source 준비 상태와 담당을 안내. 샘플 재고를 실제 재고처럼 채우지 않음 |
| 데이터 로딩 | 자리 유지 skeleton, 이전 원본의 시각 유지. 읽는 동안 기존 데이터가 갱신된 것처럼 보이지 않음 |
| 관측 없음·오래됨 | “미관측 / 관측 오래됨”, source/원본 시각/부족 조건. 0·빈 칸·가용으로 치환하지 않음 |
| 계획 중 새 revision 도착 | 선택과 기존 계획을 보존하고 “기준이 변경됨 — 재검토 필요”. 원래 계획을 자동 수정/전송하지 않음 |
| ARM 제안 접수 | “제안 접수 / Fleet 승인 대기”. 접수 번호를 보존하고 자동 admit하지 않음 |
| TRIP 조작 | 일반 “승인 대기”로 표시하지 않음. 계약이 개방된 경우에만 즉시 접수·주행 가능성을 별도 확인 |
| 원격 응답 유실 | “접수 여부 대조 중 / 업무 보류”, 원래 key를 읽음. 사용자에게 반복 클릭을 요청하지 않음 |
| Action SUCCEEDED | “로봇 동작 성공”, 별도 물리/업무 근거 상태 유지 |
| receipt 아직 없음 | pending code는 정상 대기. “근거 확인 중”과 마지막 조회 시각; 오류 토스트 반복 금지 |
| 취소 요청 ACK | “취소 요청됨 — 실제 정지/점유 대조 중”. 즉시 완료/자원 비움으로 바꾸지 않음 |
| HOLD/UNKNOWN | 보류·불명과 영향 범위를 상시 표시. 재시도·해제 대신 원래 실행 대조와 담당 인계 |
| 401/세션 만료 | 화면·요청 identity 보존, 다시 인증. 이전 쓰기 요청 자동 재전송 없음 |
| 403 | 권한/범위를 설명하고 담당 인계. 다른 자격 증명 입력란을 띄워 우회하지 않음 |
| 409 | 오류 code별로 계획 충돌·요청 key 충돌·정상 receipt 대기를 구별 |
| 503/연결 단절 | 데이터 원본 시각을 유지하고 의존 조작 비활성. 오프라인 승인·출발·확인 제출 큐 없음 |
| 여러 사용자/중복 탭 | 서버 row version 충돌을 표시하고 새 snapshot 비교. 마지막 저장으로 덮어쓰기 금지 |

## 6. 조작 규칙

- `UX-03` ARM 버튼은 **팔 작업 제안**, 취소는 **취소 요청**이다. 계획·접수·승인·수행·업무 완료를 모두 “실행”으로 부르지 않는다.
- `UX-04` 화면에서 disabled 사유를 같은 조작 근처에 항상 보여 준다. 비활성 tooltip만으로 전달하지 않는다. 서버가 다시 검사하므로 버튼 활성 자체가 허가 증명은 아니다.
- `UX-05` 원본 ID·시각·source·revision·mission/attempt를 근거 상세에서 읽고 복사할 수 있다. 기본 행에는 업무에 필요한 요약을 먼저 보인다.
- `UX-06` 사용자의 확인은 조건이 구체적인 단일 대상에 결속된다. 정상 완료에 일반 “완료 처리”·“퇴피 확인됨” 수동 토글을 만들지 않는다.
- `UX-07` Fleet 인계는 앱 열기와 ID 복사부터 제공한다. 실제 ARM 상세 deep link와 승인 화면이 구현·검증되기 전 URL을 꾸며 연결하지 않는다. 토큰을 URL에 넣지 않는다.
- `UX-08` 위험 대응은 현장 물리 급정지 수단과 Fleet 안전 운영 경로로 안내한다. 단순 Fleet 링크를 “긴급 정지” 버튼처럼 표현하지 않는다. Harbor의 제안 취소가 실제 급정지를 보장한다고 쓰지 않는다.

## 7. PC·태블릿·접근성

초기 설계 기준: PC 1280×800~1920×1080, 태블릿 약768×1024와 회전 화면. 실제 기기 목록은 미확정이며 이 수치는 검증할 viewport이지 실물 규격이 아니다.

PC에서는 좌측 업무 탐색, 중앙 단계/재고, 우측 현재 조건 상세를 사용한다. 좁아지면 상세를 독립 페이지/탭으로 옮기고 필수 식별 정보를 줄이지 않는다. 태블릿에서는 대상 ID·확인 내용·남은 유효 상태·두 가지 조작을 우선한다. 표는 중요 열을 유지한 행 상세로 전환하고, 숨긴 열에만 차단 이유를 두지 않는다.

키보드 탐색·명확한 focus·표 header·스크린리더 상태 안내를 설계 수용 항목으로 둔다. 상태는 색+텍스트/아이콘으로 표현한다. 충분한 터치 영역, 확대 시 줄바꿈, 시간 초과 전 안내, 자동 화면 이동 금지를 적용한다. 이는 설계 요구이며 WCAG 준수를 이미 검증했다는 주장은 아니다.

시각 방향은 기존 H 아이콘과 브랜드 자산을 보존하되 업무 정보의 위계·선택 상태·경고 이유를 먼저 정한다. 경고색을 장식 강조와 혼용하지 않고 기본 글꼴은 읽기 쉬운 한글 지원 sans를 검토한다. 구체 색상값·서체·component token은 픽셀 시안의 검토 결과로 확정한다.

## 8. 갱신과 사용성 검증

읽기 갱신 방식은 첫 버전에서 서버 조회를 권장한다. 주기 자체를 freshness로 삼지 않고 각 source의 원본 시각·허용 기간을 서버가 계산한다. 잦은 갱신이 선택 행·스크롤·키보드 focus를 바꾸지 않아야 한다. 태블릿의 남은 유효 표시는 참고이며 제출 시 서버가 재검사한다.

현장/관제 참가자가 설명 없이 “현재 무엇이 막혔는가”, “다음 조작의 효과는 무엇인가”, “업무가 완료됐는가”를 구분하는지 평가한다. 완료 시간 목표·목표 오조작률·현장 장갑/시야/네트워크 조건은 첫 관찰에서 정하고 임의 성능 수치를 성공 근거로 만들지 않는다.
