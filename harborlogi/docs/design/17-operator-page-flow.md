# 페이지별 업무와 이어지는 조작

2026-10-25 구현 기준. Django·PC 관제/태블릿 현장·기존 HarborLogi 로고와147개 토큰을 유지한다. 첫 화면은 조치 필요 중심이며 페이지마다 입력/판단/산출물/다음 행동을 명확히 한다. [연동 파이프라인](18-harbor-rosy-pipeline.md)을 함께 따른다.

| 페이지 | 사용자의 일 | 결과와 다음 행동 |
|---|---|---|
| 운영 현황 | 막힌 업무와 다음 담당을 찾음 | 원래 실행 대조, 반출 검토, 현장 확인/유효시간 갱신으로 이동 |
| 반출 관제 | 지시된 그룹/순서와 보류 사유 확인 | 같은 요청의 야드·계획·실행·근거 작업 공간 |
| 화물 | ID·크기·제원을 준비하고 이력을 확인 | 해당 화물로 요청 등록 또는 기존 요청 조회 |
| 크기 원본 | 현재 크기를 확인하고 새 크기를 선언 | 최신 크기로 폼을 초기화. 과거 관측/계획은 당시 원본 유지 |
| 업무 요청 | 입고/반출 종류와 우선순위를 저장 | 반출은 선택한 관측으로 검토, 입고는 같은 요청의 현장 회차 배정 |
| 재고·관측 | 출처/시각/구역/보유/점유 영역 확인 | 선택한 관측 ID를 유지한 채 반출 요청 선택→계획 검토 |
| 반출 작업 공간 | 원본과 예상 이동을 대조하고 지시를 변경 | 원래 실행이 있으면 재제출보다 대조 우선; 없으면 지원된 인계 조건 확인 |
| 실행·대조 | Harbor 접수·ROSY 승인/수행·물리 receipt·업무 근거 구분 | 상태에 맞는 주 조작 하나, 독립 승인 화면 인계, 원래 key로 조회/사유 있는 취소 |
| 현장 확인 | 배정된 화물·차량·회차를 직접 확인 | 신선한 CLEAR는 출발 전제 기록, 만료/불일치는 새 회차 배정, 출발은 Fleet 운영자가 별도 실행 |
| 기록·검증 | 특정 업무/객체의 원본을 추적 | 객체 종류와 업무 scope를 유지해 해당 요청·계획·실행·현장/크기로 복귀 |
| 업무 안내 | 정상 흐름·담당 분리·예외 복구 확인 | 내 역할의 시나리오를 먼저 보이고, 내가 열 수 있는 화면에만 링크한다. 다른 역할의 시나리오는 접어 둔다. 기술 API 정보는 접힌 보조 참조 |
| 설정·연동 | 설치 원본과 연결 준비 수준 확인. 계정 관리 링크는 staff 계정에만 보인다 | 설정 있음/접속 확인/지원 계약/관측·근거/실물 수용을 합치지 않음 |

## 맥락을 보존한다

관측 선택은 `?observation=<id>`로 요청 목록·등록·상세까지 유지한다. 알려지지 않은 선택을 최신 원본으로 조용히 바꾸지 않는다. 선택한 원본은 PlanForm의 실제 ModelChoice 검증을 통과해야 한다. 신규 요청에는 `?cargo=<id>&kind=...`를 받아 재입력을 줄인다. 현장 배정에는 `?order=<id>`를 받아 입고 요청을 유지한다.

`workspace_context(order, plan=None, *, priority_form=None, plan_form=None, review_observation=None)`는 기존 고정 Plan의 그림/원본을 바꾸지 않는다. 계획이 없을 때만 검토 대상으로 선택한 관측을 지도에 사용한다. 현재 재검토 폼의 원본과 저장된 계획 원본이 다르면 둘의 출처/revision을 명시한다. POST 유효성 오류는 선택과 입력을 보존한다.

업무 기록 URL의 `?order=<id>`는 Order+그 업무의 Plan+Command+현장 회차/확인/출발 전제만 포함한다. 일반 `?object_type=...&q=<id>`는 숫자 ID만 같고 다른 종류인 기록을 섞지 않는다. 필터 상태와 해제를 표시한다.

## 현장 확인의 유효시간과 다음 담당

직접 확인 시각부터5분을 넘거나 미래 시각인 CLEAR는 출발 전제로 사용할 수 없다. `confirmation_fresh`, `confirmation_expires_at`, `needs_new_confirmation`, `can_prepare_departure`를 서버에서 계산한다. 만료한 화면에는 실패할 출발 버튼을 내지 않고 operator에게 기존 재배정 서비스를 통한 새 회차 배정을 제공한다. field-only 사용자는 자기 확인과 담당자 재배정 필요를 보고, 스스로 권한을 높이지 않는다. 이전 확인/회차를 덮어쓰거나 버튼 클릭으로 시각을 갱신하지 않는다.

입고 요청 상세에는 `episode_rows`(episode/confirmation/departure/freshness/next action)를 제공한다. 출발 전제는 실제 Fleet TRIP 접수가 아니며 기존 명명 운영자 실행 경계를 유지한다.

## 표현과 검증

새 장식/차트 대신 작업 목적·현재 판단·다음 행동을 우선한다. raw 상태·긴 key·digest는 보조 상세에 남긴다. 보류를 성공 색으로 표시하지 않으며 한 화면에서 Harbor/ROSY/관측/업무 완료를 같은 상태로 축약하지 않는다. 기존 의미 토큰으로 구성하고, 주요 조작/권한/빈 상태/오류/뒤로 가기/선택 원본·회차·기록 scope·만료를 서버와 네 화면 폭 브라우저에서 검증한다.
