# Harbor 업무 실행기와 ROSY 연동 경계

2026-10-26 설계, 2026-10-29 구현 현황 정리. 책임 결정:
[ADR0013](../adr/0013-independent-business-execution-and-platform.md).
상시 실행기·업무 근거 연결과 ARM 대조 경계의 현재 구현은 「지속 실행과 복구」에
구분해 적는다. 아래 개념 인터페이스는 Harbor 내부 책임을 설명하며 새로운 ROSY
API 필드나 실물·운영 수용을 선언하지 않는다.

## 사용자가 얻는 결과

사용자가 목표 배치를 확정하면 Harbor가 실행 의도를 영속 저장한다. Harbor는 필요한 작업을 순서대로 요청하고 결과를 확인해 계속 진행한다. 화면에서는 목표·관측·실행 중 작업·남은 단계·보류 이유를 같은 업무에서 확인한다. 화면을 닫아도 실행기 책임이 유지된다.

예를 들어 C2 임시 이동, C1 반출, C2 재적재가 필요한 계획이라면 세 단계의 업무 의존 관계는 Harbor에만 있다. 각 단계의 실제 이동·팔 제어·자원 점유는 ROSY가 처리한다. Harbor는 C2의 필요한 위치·퇴피 근거가 확보되기 전 C1 단계를 제출하지 않는다. 실패 복구가 원래 목표를 변경하면 별도 계획 revision으로 남긴다.

## 구성과 데이터 소유

| Harbor 내부 구성 | 역할·입출력 | 두지 않는 책임 |
|---|---|---|
| 웹 application service | 계정·역할·확정 범위·revision 검사, 실행 의도 저장, 조회 결과 제공 | 장치 제어, 페이지 GET에 따른 업무 진행 |
| 업무 실행기 | 확정 계획·단계·근거를 읽고 다음 업무 전이를 선택, 제출/대조 의도 기록 | HTTP 스키마 해석, 로봇 경로·실제 자원 claim |
| 업무 저장소 | 업무 상태, 단계별 시도·원본 대응, 변경 감사, 중복 수신 억제 | ROSY 실행 원장의 복제 또는 수정 |
| ROSY 연동 어댑터 | 공개 API 인증·호환 검사, 설치 binding, 요청/조회/취소, 원본 결속 검증, 앱 결과로 변환 | 재취급·우선순위·업무 완료 판단 |
| 업무 근거 어댑터 | 인증된 producer의 배치·위치·퇴피 자료를 현재 업무·실행에 결속 | 장치 자격으로 측정을 꾸미거나 가상 배치를 관측으로 승격 |

배포의 서비스 개수와 책임 분리는 별개다. 첫 구현은 기존 Harbor 서비스의 lifecycle에 실행기를 통합해 단일 writer 제약을 유지한다. 별도 worker 프로세스·queue 서비스·새 DB는 먼저 도입하지 않는다. Django DB와 외부 업무 SQLite 사이의 원자성을 가정하지 않고, 저장 의도·원래 key·복구 대조로 중단 지점을 처리한다. 다중 worker는 별도 저장·lease·복구 설계가 검증된 뒤 확장한다.

## 실행기가 보는 내부 계약

현재 코드 경계는 다음과 같다. `harbor_web/executor.py`는 처리 대상·주기·backoff만
선택하고 `commands.advance_command()`를 호출한다. 최초 제출과 다음 단계 제출은
같은 명령 서비스에서 `BusinessLedger.submit()`의 검증된 결과를 사용한다.
`propose()`의 mission ID 반환과 TransportLedger의 job dict 반환은 호환 진입점이다.

`harbor/execution.py`가 ARM·Cell·TRIP HTTP 결과를 하나의 `ExecutionSnapshot`으로
변환한다. Harbor 진행 의미와 원래 key/mission/attempt, 원본 job/receipt를 함께
보존한다. 원본 wire 요청·digest·결속 검사는 `fleet_contract.py`가 소유하며 기존
binding 메서드는 여기에 위임한다. 업무 장부는 정규화 결과와 독립 업무 근거로
전이를 판단한다. Cell compile은 제출 의도 저장 전 수행하고, 그 뒤 stage CAS를
통과해야 POST할 수 있다.

`harbor/ledger.py`가 저장 payload 해석, read-only 조회와 소비한 근거 조회를 소유한다.
조회는 DB를 생성하거나 복구하지 않는다. Workbench는 Fleet 조회 뒤 장부를 다시
읽어 version·digest·mission·단계·상태가 바뀌면 STALE로 표시한다. 화면은 어댑터의
진행 의미를 표시하며, 장부 HOLD와 Fleet 수행 상태는 각각의 소유권을 유지한다.

아래 이름은 Harbor 소유의 개념 계약이다. 별도 범용 framework나 ROSY SDK를 만들라는 요구가 아니다. 기존 `rosy_http.py`와 `ArmTransferBinding`을 활용하고 필요한 최소 seam만 둔다.

| 연산 | 입력 | 출력과 보장 |
|---|---|---|
| 제출 | 불변 단계 의도, 검토된 설치 binding, 안정적인 request key | 접수 여부·원본 실행 참조·원본 응답 근거 또는 결과 불명. 접수는 승인/완료가 아님 |
| 대조 | 원래 request key와 저장된 실행 참조 | 검증된 실행 상태·관측 시각·관련 근거 참조. key/body/mission/principal 불일치는 진행 거절 |
| 취소 요청 | 원래 실행 참조, 사유, 기대 업무 version | 취소 요청 접수/거절/불명. ACK로 실제 정지나 점유 해제를 표시하지 않음 |

어댑터 결과에는 적어도 원래 요청 식별, 원본 실행 식별, 처리 상태, 원본 코드·조회 시각이 필요하다. 원본이 제공하는 attempt/digest/generation은 해당 계약에 맞춰 보존하며 제공하지 않는 값은 미확인이다. 새로운 ROSY endpoint·필드·지원 협상을 이 문서에서 만들어 쓰지 않는다. 현행 공개 경로는 [platform-contract](../platform-contract.md)와 [설계18](18-harbor-rosy-pipeline.md)을 따른다.

정규화는 Harbor가 알아야 하는 진행 의미만 표현한다. API에 없는 물리 성공이나 전체 완료를 합성하지 않는다. 알 수 없는 상태·schema·누락된 필수 필드·인증 실패는 명시적인 연동 오류로 보류한다. 전송 재시도와 새 실행은 구분한다. read-after-timeout의 not-found도 즉시 미제출을 확정하는 근거로 삼지 않으며, 기존 계약의 대조 절차 없이 자동 재전송하지 않는다.

## 지속 실행과 복구

1. 확정 transaction은 계획 ID/digest·관측/설치/크기 원본·사용자·확정 범위를 고정하고 실행 의도를 저장한다. 아직 전송되지 않은 의도가 crash 뒤 복구 가능해야 한다.
2. 실행기는 의존 단계 완료·현재 revision·관련 관측·권한·설치 대응을 확인하고 단계 의도와 request key를 먼저 보존한다. lease/업무 version으로 동일 단계의 중복 진행을 막는다.
3. 네트워크 호출은 DB transaction을 길게 잡은 채 수행하지 않는다. 응답 저장은 기대 version·원래 요청에 결속한다. 중간 crash는 같은 원본 조회로 복구하며 새 요청 key를 생성하지 않는다.
4. 승인 대기·자원 대기·실행 중에는 원래 작업을 대조한다. 초기 구현은 서버의 제한된 polling을 사용하고 조회 간격·한 번에 처리할 업무 수·backoff를 설정으로 제한한다. 화면 polling은 읽기만 한다. 공개 이벤트 계약이 검증되기 전 내부 ROSY 버스에 붙지 않는다.
5. 물리 결과와 업무 근거가 갖춰지면 해당 단계를 완료한다. 후속 단계는 동일한 확정 범위 안에서 자동 진행한다. 전체 목표 배치 검증이 끝나야 업무가 완료된다.
6. 서비스 재시작·복원·버전 변경 시 저장 의도·원래 실행부터 대조한다. 기존 restore reconciliation 차단과 WriterLease를 유지한다. 네트워크 단절에서 실행기를 계속 바쁘게 재시도하거나 불명을 성공으로 바꾸지 않는다.

`BusinessLedger`는 실행 대조와 업무 전이를 맡는다. `confirm()`은 단계 근거를,
`finish()`는 최종 업무 근거를 검증한다. 현재 상시 실행기는 이 두 전이를 연결하며,
업무 근거 provider는 명시적으로 설정해야 한다. 미설정 Registry는 진행을 허용하지
않는 placeholder 출처를 유지한다. Fleet 조회만으로 다음 단계가 열리지 않는다.
Command binding은 불변이므로 재계획을 원래 Command에 덮어쓰지 않는다.

2026-10-28 ARM 대조 구현: `harbor/execution.py`가 기존 binding 검증으로
job·physical receipt를 원래 request key·mission·principal에 결속하고,
`ArmExecution`으로 실행 참조·물리 목표 확인·HOLD를 제공한다. 원본 job·receipt와
attempt·digest·epoch·generation은 감사 근거로 보존한다.
`BusinessLedger.reconcile_arm()`은 이 한 번의 조회 결과로 장부를 갱신한다.
웹과 상시 실행기는 `reconcile_command()`를 함께 사용하며, 감사 기록에도 같은
결과를 저장한다. 상시 실행기만 bookkeeping HOLD의 재진입을 요청하고, Fleet HOLD와
취소 대기는 유지한다. 물리 목표 확인은 `confirm()`·`finish()`의 독립 업무 근거를
대신하지 않는다. 이 구현은 아래의 실물·운영 수용 조건을 충족했다는 뜻이 아니다.

## 상태와 변경 정책

업무 화면은 계획 검토, 사용자 확정, 제출 처리, ROSY 승인/자원 대기, 실행 중, 업무 근거 대기, 보류/결과 불명, 취소 대조, 완료를 구별한다. 실제 저장 enum과 migration은 구현 때 확정하고 기존 상태를 재해석해 덮어쓰지 않는다. ROSY 상태와 Harbor 업무 상태는 1:1 대응하지 않는다.

| 상황 | Harbor의 조치 | ROSY의 조치 |
|---|---|---|
| 확정 범위 안 정상 진행 | 근거 확인 뒤 다음 단계 요청 | 승인 정책·자원·안전 검사와 실제 실행 |
| 업무 순서/목표 변경 | 미제출 단계 보류, 영향 비교·새 계획, 범위 밖이면 사용자 확정 | 기존 제출 작업의 상태·취소 결과 제공 |
| 로봇/팔 오류 | 원래 단계 보류 및 업무 영향 표시 | owner 복구·정지·실행 상태 관리 |
| 통신·결과 불명 | 후속 단계 차단, 원래 key 대조 | 원래 실행 조회·복구 가능한 사실 제공 |
| 관측과 목표 불일치 | 새 관측으로 남은 업무 재검토 | 관측·실행 결과 제공; 항만 목표를 임의 변경하지 않음 |
| 취소 | 후속 단계 차단, 실제 정지·점유 근거 확인 | 계약에 따른 취소·정지 수행과 결과 제공 |

여러 Harbor 업무의 논리 충돌은 Harbor가 검토한다. ROSY가 자원 admission을 통과시켰다고 해서 서로 다른 계획의 최종 화물 배치가 업무상 양립한다고 보지 않는다. 첫 구현은 동시에 진행할 업무를 제한하며, 공동 계획·병렬 재배치는 별도 검증 전 활성화하지 않는다.

## 화면별 책임

- 관제: 실제 관측 물량, 실행 중 업무, 근거 부족·승인/자원 대기, 개입할 이유를 표시한다. 예상 이동 수를 실제 처리량으로 집계하지 않는다.
- 업무 상세: 확정 목표/원본 배치, 단계별 실제 결과/근거, 남은 작업, 원래 요청·재계획 이력과 허용 조작을 표시한다.
- 3D 배치: 목표 편집·예상 순서·실제 관측을 구별한다. 가상 재생 완료가 업무 완료를 발생시키지 않는다.
- 설정: 설치 참조와 연동 상태를 확인한다. Fleet 승인 정책·실제 자원 claim 설정의 별도 정본을 만들지 않는다.

## 검증과 현재 결손

이 설계 문서와 ARM 대조 구현만으로 실물·운영 수용이나 ARM 정책 admission이
완료되지는 않는다. 상시 실행기와 업무 근거 연결의 구현 존재를 실제 producer의
인증·설치·현장 수용으로 계산하지 않는다. 배포 차단과 명시적 활성화 조건을 유지한다.

수용 시험은 다음을 포함한다: 화면 종료 뒤 3단계 합성 업무 진행, 동일 이벤트/조회 반복의 단일 전이, 전송 전후 crash와 재시작, timeout 뒤 중복 없는 대조, 부분 완료 후 재계획, 취소 ACK 뒤 후속 단계 차단, 잘못된 identity/schema/근거 거절, restore 차단 유지. Harbor 단독 시험과 고정 양 끝 HTTP 계약 시험, 실제 장치·현장 수용은 각각 기록한다.

핵심 독립성 시험은 Harbor의 재취급 순서를 바꿔도 ROSY를 수정하지 않는 것, ROSY의 공개 계약을 유지한 구현 교체가 Harbor 업무 규칙에 영향을 주지 않는 것이다. binding 변경·계약 breaking change는 자동 흡수한다고 약속하지 않는다.
