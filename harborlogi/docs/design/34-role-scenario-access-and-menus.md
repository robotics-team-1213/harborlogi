# 역할 시나리오별 화면 권한과 메뉴

상태: 2026-11-14 설계·구현 계획. 사람 책임 역할은 [역할 설계](01-roles-and-workflows.md), 경로·동작 권한의 정본은 [제품 웹 계약](13-product-web-surface.md)이다. 이 문서는 두 문서를 페르소나 시나리오로 묶어 **화면 접근·메뉴 노출·안내의 단일 원본**을 정한다. 실제 인원·겸임 정책은 여전히 미확정이며 담당자를 합성하지 않는다.

## 1. 왜 정리하나

2026-11-14 origin/main `65d7cca`를 역할별로 실측했다(합성 데이터, Django 시험 클라이언트). 권한 위반·403 링크는 없었다. 문제는 원본이 흩어진 것이다.

- 화면 접근은 각 view의 `require_roles(...)`, 메뉴 노출은 `base.html`의 `can_*` 조건, 머리 경로 이름은 `base.html`의 긴 `section` 분기, 안내는 `workflow.html`의 조건에 따로 적혀 있다. 하나를 바꾸면 나머지가 어긋나도 시험이 잡지 못한다.
- 메뉴는 9개 항목의 평면 목록이다. 누가 어떤 일을 하러 들어왔는지(업무 처리·현장 확인·설치 관리)가 메뉴에 드러나지 않는다.
- 사이드바 아래에 그룹 이름(`admin`, `operator`)이 영문 그대로 보인다.
- 역할이 없는 계정의 403 화면은 “운영 현황으로 돌아가기”를 보여 주는데, 그 화면도 403이다. 현장 확인만 가진 계정도 같은 링크를 본다.
- 설정의 계정 관리 링크(`/admin/`)는 staff가 아닌 admin 계정을 Django 관리 로그인으로 돌려보낸다.
- 개발 미리보기 계정은 네 역할을 모두 가진 한 계정뿐이라 역할별 화면을 직접 볼 수 없다.

## 2. 페르소나

| 페르소나 | 계정 group | 하러 오는 일 | 기본 진입 |
|---|---|---|---|
| 업무 담당 | `operator` | 화물·요청 등록, 관측 선택, 계획 검토·제안, 실행 대조, 현장 회차 배정, 측정 기록 | `/` 운영 현황 |
| 현장 확인 담당 | `field` | 자기에게 배정된 회차의 차량·화물 확인과 결과 기록 | `/field/` |
| 설치·운영 관리 | `admin` | 구역 맵·설치 기준, 관측 원본 등록, Fleet 연동 확인, 계정 발급 | `/` 운영 현황 |
| 조회 | `viewer` | 현황·업무·기록 읽기 | `/` 운영 현황 |

겸임은 group을 함께 부여한다. 관리 역할이 업무 실행 권한을 자동으로 갖지 않는다(01 §1).

## 5. 메뉴

메뉴는 시나리오 묶음으로 나눈다. 묶음 제목은 펼친 메뉴에서만 보이고, 접힌 메뉴는 구분선만 남긴다(제목은 화면 읽기 프로그램에 남긴다). 사용자가 열 수 없는 화면은 메뉴에 두지 않는다. 항목이 하나도 없는 묶음은 제목도 그리지 않는다.

| 묶음 | 항목(순서) | 보이는 역할 |
|---|---|---|
| 업무 처리 | 운영 현황, 반출 관제, 화물·요청, 실행·대조, 자동 재배치 | 조회·업무 담당·관리 |
| 재고·근거 | 재고·관측, 기록·검증 | 조회·업무 담당·관리 |
| 현장 | 현장 확인 | 현장 확인·업무 담당·관리 |
| 관리 | 설정·계정 | 관리 |
| 도움말 | 업무 안내 | 모두 |

사이드바 아래 역할 표시는 페르소나 이름(업무 담당·현장 확인·설치·운영 관리·조회)을 쓴다. 머리의 현재 위치 이름도 같은 원본에서 읽는다.

## 6. 안내와 예외 화면

- **업무 안내(`/workflow/`)**: 내 페르소나의 시나리오를 먼저 보여 준다. 각 단계는 내가 열 수 있는 화면이면 링크, 아니면 담당 이름을 붙인 글자로 둔다. 다른 페르소나의 시나리오는 접힌 “다른 담당의 일”에 둔다. 기존 안내 문구(현재 운영 연결의 범위, Fleet 인계)는 유지한다.
- **403**: 돌아갈 곳을 역할로 고른다. 업무 화면을 읽을 수 있으면 운영 현황, 현장 확인만 있으면 현장 확인, 역할이 없으면 “역할이 아직 없습니다”와 비밀번호 변경·로그아웃만 둔다.
- **계정 관리 링크**: active staff인 admin에게만 링크를 준다. 아니면 “계정 관리에는 staff 권한이 필요합니다”를 보여 준다.

## 7. 개발 미리보기 페르소나 계정

`tools/product_preview.py`는 기존 네 역할 겸임 계정에 더해 페르소나별 계정 네 개를 만든다. 비밀번호는 실행마다 새로 만들지 않고 비공개 `runs/product-preview/access.json`의 `personas`에 둔다. 관리 계정만 staff다. 합성 현장 회차는 현장 확인 계정에 배정한다. 개발 DB 전용이며 운영 seed 계정이 아니다.

## 8. 결정 (에이전트 판단, 사용자 검토 대상)

- 접근 규칙은 바꾸지 않는다. 실측 행렬이 13과 맞고, 바꿀 근거가 되는 사용자 결정이 없다.
- view의 `require_roles` 데코레이터는 그대로 두고, 새 원본 `harbor_web/access.py`와 HTTP 행렬 시험으로 둘이 어긋나지 않게 묶는다. 열린 팀 브랜치(KAN-115·118)가 `views.py`·`urls_product.py`를 고치고 있어 데코레이터를 일괄 교체하면 충돌이 커진다.
- 시나리오 실행 순서를 강제하는 마법사나 페르소나 전환 기능은 만들지 않는다. 화면 폭으로 역할을 추정하지 않는다(08 §5).
