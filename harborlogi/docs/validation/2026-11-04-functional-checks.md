## 미해결: 종합 브라우저 검사의 화면 가정 불일치

- **관측:** 기존 `product_web_browser_check.py:148`에서 `[data-yard-view="flat"]`을 누르다 30초 시간 초과가 났다. 같은 실패를 두 번 관측했다. 브라우저 오류는 요소를 찾았으나 보이지 않는다고 명시한다.

- **다음 확인:** 테스트가 데스크톱의 동시 표시와 작은 화면의 전환을 각각 검증하게 고친 뒤, 종합 시나리오 전체를 다시 실행한다. 숨은 버튼 강제 클릭이나 검증 삭제로 통과시키지 않는다.

## 기존 현장 설치 읽기 전용 확인

기존 비공개 접속 설정을 사용해 관제 PC에 접속했다. 실제 Fleet 컨테이너는 healthy이고, 설치된 CA로 인증서를 검증한 HTTPS `/healthz`는 `200 {"status":"ok"}`였다. 기존 운영자 진단 자격으로 `GET /api/fleet/session`·`GET /api/fleet/state`를 조회했다. 이 자격을 Harbor 서비스 설정으로 복사하거나 작업을 제출하지 않았다.

Fleet에 등록된 로봇은 4대이며 관측 시점 온라인은 1대였다. 온라인 장치는 `IDLE`, CORE 진단 `OK`였지만 모터 관측은 `unavailable`이었다. OMX 팔 상태·관측 브리지와 top·side·양 손목 카메라 서비스가 실행 중이었다. 서비스 실행은 물리 동작이나 화물 인계 성공의 증거가 아니다. Harbor용 `service` 신원 등록도 확인했다. 주소·실제 계정·토큰은 기록하지 않았다.

실물이 없다는 문제가 아니라, 현재 실물의 동작 수용을 입증할 모터·물리 관측과 감독 조건이 별도로 필요하다. 이 작업에서 실물 동작·서비스 재시작·운영 설정 변경은 하지 않았다. 실제 Fleet 소스의 격리 통합 검증은 아래 후속 결과에 별도로 기록한다.

CE 재판정: 해당 없음 — 해결한 테스트 표현 불일치와 시간 초과 복구는 최종 코드·회귀 테스트·이 기록으로 재구성할 수 있어 별도 해결 교훈을 늘리지 않았다. 실물 수용은 미실행으로 구분한다.

## Linux 시험 PC의 실제 Fleet 소스 연동

Harbor `3ea78da5cf9c17c557437336d003e5d82d32fc2f`와 ROSY Platform `ed455ea03af48100085c32487ba11a56ce80c085`를 깨끗하게 체크아웃해 기존 `tools.integration.real_fleet_http --full-flow`를 Linux 시험 PC에서 실행했다. 팀 저장소를 원본으로 명시하고 기존 nightly의 격리 Python 환경을 재사용했다.

결과: 1개 통합 테스트 통과, 실패·건너뜀 없음, 종료 코드 `0`. 한 Fleet의 TRIP·ARM HTTP, 반출 전 변경 지시, 재취급, 이송, S 내려놓기, 정리·팔 퇴피 및 독립 재확인까지 6개 단계 모두 통과했고 업무 장부는 `COMPLETED`였다. 합성 UDS 제출 3회·조회 3회와 `PRE_DISPATCH`·`POST_ACTION`·`RECHECK` 증거를 확인했다.

보고서·로그를 로컬 `runs/real-fleet/full-flow-3ea78da.{json,log}`로 회수했다. 이 검증은 실제 Fleet 구현과 합성 owner·관측을 연결한 것으로, 운영 설치에서 실제 로봇이 화물을 옮겼다는 증거가 아니다.

추가 독립 리뷰에서 부모가 먼저 종료되고 자식이 stdout 핸들을 보유하면 기존 파이프 수집이 멈추는 Windows 예외를 재현했다. 출력을 임시 파일에 직접 기록하고 검사 부모의 종료만 기다리도록 바꿨다. 프로세스 트리 종료 도구 실패도 진단으로 보존하고 직접 자식은 회수한다. 종료한 부모의 stdout을 붙잡은 자식, 트리 종료 실패, 일반 타임아웃의 자식 리스너 정리를 포함한 실행기 회귀 9개가 통과했다. 이미 종료한 Windows 부모가 분리해 남긴 프로세스 감독은 지원하지 않으며, 현재 브라우저 하네스는 정상 종료 시 자체 서버를 정리한다.
